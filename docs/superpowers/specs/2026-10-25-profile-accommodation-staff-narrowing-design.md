# Profile Fields, Accommodation Requirements, Local Info Cleanup, and Staff Role Narrowing — Design

## Context

This is a 7-part change request from the user, covering several independent subsystems. Decomposed here into one combined spec (not split into separate sub-project specs) because 6 of the 7 items are small and share no meaningful complexity; only item 6 (Staff role narrowing) is large, and it's kept in this same spec because it's the dominant item and doesn't benefit from separate sequencing — everything here can land in one plan with clearly separated tasks.

A pre-implementation research pass (via a research subagent) established the following, which changes the shape of several items from how the original request assumed them:

- **"My Profile" currently has no name/email/phone/photo fields at all.** It only contains Emergency Contacts and Accommodation forms. `profiles.full_name`/`profiles.email` are set once at signup (via the `handle_new_user()` trigger) and have never been user-editable anywhere in this codebase. No profile-picture/avatar column or UI exists anywhere.
- **Accommodation is a real, existing form** (`application_accommodation` table: `hotel_name`, `room_number`, `location_note`, all nullable) with zero validation today, client or server.
- **"Safety & Health" is not a dedicated page/route.** It's one content section (with 3 items: Water, Currency, Prayer times) inside the generic, database-driven "Local Info Hub" feature, which participants see post-login at `/local-info`. Deleting it is a data operation, not a code deletion.
- **The emergency-line text "COY21 Emergency Line +90 555 000 1111" does not exist anywhere in the codebase.** The real current value is a placeholder: `local_info_items` row with `label = 'COY21 Emergency Line'`, `value = 'TBC by Organising Team'`, inside a separate "Emergency Numbers" section (siblings: Police, Ambulance, Fire). This is the row to update.
- **"Key Contacts" already exists** as another Local Info Hub section (Registration Desk, Info Desk, Medical Point, Lost & Found). The two new email contacts are added as two more items in this same section, visible to participants post-login — confirmed with the user this is the intended audience (not the pre-login public Contact page).
- **The `staff` role was deliberately broadened to near-total system access exactly one month before this request** (2026-09-29 "staff role consolidation" — see `docs/superpowers/specs/2026-09-29-staff-role-consolidation-design.md`), collapsing 7 narrow domain roles into one. This request reverses that decision for `staff` specifically. Confirmed with the user: no currently-active staff account needs anything beyond scanning/attendance today, so this is a straight redefinition of what `staff` means, not a resurrection of the old 7 sub-roles. `super_admin` is unaffected and continues to have full access.

## Scope boundaries (explicitly confirmed, not to be second-guessed during implementation)

- Items 3/4/5 (Local Info content) are **data edits via the existing admin Local Info editor**, not new code, except where the rendering template needs `tel:`/`mailto:` link support added (checked in Task 1 below).
- Item 1 adds 4 **new** fields to My Profile (name, email, phone, profile picture) — this is new feature work, not a validation tweak on existing fields.
- Item 2 adds validation to the **existing** 3 accommodation fields; `room_number` is explicitly exempt.
- Item 6 redefines `staff`'s own RLS/route access down to scanner + attendance only. It does **not** reintroduce the old 7 sub-roles. It does **not** change `super_admin`.
- `scanner_device` (the existing, separate, narrow role used for dedicated kiosk/scanner-only devices) is the access-shape template for the new narrow `staff`, but `staff` and `scanner_device` remain **distinct roles** — `staff` is a human staff member's personal login (lands on a shell with their name, not the bare kiosk `/scanner` UI), scoped to exactly the same two capabilities (scan QR, view/manage attendance), not merged into `scanner_device` itself.

## Design

### 1. My Profile: add Name, Email, Phone, Profile Picture (required)

**Where:** `src/app/[locale]/(participant)/(shell)/my-profile/page.tsx` and `profile-forms.tsx` gain a new `IdentityForm` section, rendered above the existing Emergency Contacts / Accommodation forms.

**Fields and storage:**
- **Name** → `profiles.full_name` (already exists, `not null`, currently never user-edited — this is the first feature to make it editable).
- **Email** → `profiles.email` (already exists, `not null`). Editing a user's auth email is a real identity change in Supabase Auth, not just a `profiles` row update — changing it must go through `supabase.auth.updateUser({ email })`, which triggers Supabase's own confirmation-email flow (the email doesn't change until the user clicks the confirmation link). **Decision: add a lightweight `on update of email on auth.users` trigger** that syncs `profiles.email` only after Supabase confirms the new email (i.e., the trigger fires on the real `auth.users.email` change, which Supabase only applies post-confirmation) — this avoids ever showing a "confirmed" email in `profiles` before the user actually confirms it.
  - **This mechanism depends on `double_confirm_changes = true`** (confirmed set in `supabase/config.toml:224` at spec-review time), which is what makes `auth.users.email` update only post-confirmation rather than optimistically. This is a stated, explicit dependency, not an implicit assumption — the implementation task must re-verify this setting matches on the *remote* linked project before relying on it (this repo has a documented history of local/remote project config and identity mismatches; do not assume local `config.toml` reflects the live project without checking).
  - **Gap found and fixed during spec review**: `supabase/migrations/20260727000000_fix_profiles_role_privilege_escalation.sql:32` already has `grant update (full_name, email) on profiles to authenticated` — meaning, as originally specified, a user could bypass the entire Auth-confirmation flow by directly `update profiles set email = '...'` via the Supabase client, writing an unconfirmed email straight into `profiles`, defeating the whole point of the new trigger. **Fix: a new migration narrows this grant to `update (full_name) on profiles to authenticated`** (dropping `email` from the directly-grantable column list) — `profiles.email` becomes writable only by the new trigger (which runs as the table owner / `security definer`, not subject to this grant), never directly by an authenticated client. The identity Server Action (`saveIdentity`) only ever calls `supabase.auth.updateUser({ email })`, never writes `profiles.email` directly, so this narrowing doesn't break the intended flow.
- **Phone** → new column `profiles.phone text`. (Not reusing `applications.phone`, which is a point-in-time application-snapshot field, deliberately separate per the existing schema comment — confirmed in research. A profile phone is the current, editable identity field.)
- **Profile Picture** → new column `profiles.avatar_path text` (storage object path, nullable) + a new private Supabase Storage bucket `avatars`. Required field, but "required" for an *already-uploaded* picture means: the form blocks save only if no picture has ever been uploaded (first-time save must include one); re-saving other fields without re-uploading a picture that's already on file is fine, since the picture doesn't need to be re-attached on every save.
  - **Concretized during spec review** (the original spec was prose-only on this point; review found this codebase has two existing bucket migrations — `import_storage_bucket`/`import_storage_policy_consolidation` and `participant_documents_bucket` — whose precedent this design must match, not improvise around):
    - Bucket created with explicit `file_size_limit` (e.g. 5 MB) and `allowed_mime_types` (`image/png`, `image/jpeg`, `image/webp`) at creation time, matching how both existing buckets are created.
    - Path-keying convention: **folder-prefixed**, not a flat filename — `{auth.uid()}/avatar.{ext}`, matching the existing codebase's established RLS pattern of `(storage.foldername(name))[1] = auth.uid()::text` (confirmed by review as the existing precedent; a flat `{uid}.ext` filename, which the original spec's wording didn't clearly rule out, would not match this pattern and should not be used).
    - Policy shape: a single `for all` policy per relevant role, not separate per-verb policies — review found this codebase's own history shows a missing UPDATE policy silently breaks `upsert: true` calls, which is exactly the operation avatar replacement needs (uploading a new photo over an existing one). Use `for all`, matching the existing buckets' current (consolidated) shape, not their original per-verb shape.
    - Staff/admin read access: **explicit decision needed and now made**. Correction from an earlier draft of this spec: the two existing buckets' actual read-all policies grant access to pre-consolidation role names (`registration_admission_manager, super_admin` on `participant-documents`; `agenda_allocation_manager, super_admin` on `import-uploads` — confirmed by reading both migrations directly), not `is_staff()` or any post-consolidation helper — there is no existing `is_super_admin()`-shaped bucket policy to literally copy. The decision for `avatars` is still made fresh, informed by that pattern's *shape* (a narrow read-all grant, not a blanket one) rather than copied verbatim: `super_admin` gets a read-all policy on the `avatars` bucket (using the new `is_super_admin()` helper from layer 8 below) for admin/support purposes; narrowed `staff` (per item 6 below) does **not** get this read-all policy, since viewing participant photos is not an attendance capability.

**Validation (client):** `IdentityForm` in `profile-forms.tsx` follows the established `requiredFieldsError` pattern (same as the 6 admin "New X" managers) — `.trim()` checks on name/email/phone, checks `avatarPath` is set (either previously-saved or newly-selected-this-session) before allowing save, single `t('requiredFieldsError')` banner on failure. A `*` suffix is added next to each of the 4 field labels.

**Validation (server):** the Server Action (`saveIdentity` in `actions.ts`) independently re-validates all 4 fields are non-empty/non-whitespace (and that an avatar path exists) before writing anything — rejecting with a clear error if not, matching the pattern the research found was *missing* from the existing Emergency Contacts/Accommodation actions. This is the first Server Action in this feature area to add real server-side required-field enforcement; Emergency Contacts/Accommodation are left as they are (out of scope — not part of this CR).

**DB constraint:** `profiles.phone` and `profiles.avatar_path` added as nullable columns (a hard `NOT NULL` constraint is not used, to avoid breaking any existing profile row created before this feature — enforcement is at the application layer, consistent with how every other "required" field in this codebase, e.g. the admin manager forms, is enforced only at the app layer, not the DB layer).

### 2. Accommodation: require hotel_name and location_note, keep room_number optional

**Where:** `profile-forms.tsx`'s existing `AccommodationForm`, `actions.ts`'s existing `saveAccommodation`.

**Client:** add a `.trim()` required check on `hotel_name` and `location_note` only (not `room_number`), `t('requiredFieldsError')` banner, `*` marker on the two required field labels (not on Room Number's label).

**Server:** `saveAccommodation` gains the same two-field required check, rejecting before the Supabase write if either is missing — this closes the real gap research found (no server-side validation existed at all for this form).

**DB:** no migration needed — `hotel_name`/`location_note` stay nullable at the DB level (same reasoning as Task 1's identity fields: app-layer enforcement, not a DB constraint, consistent with this codebase's existing pattern).

### 3/4/5. Local Info Hub content changes

All three are **data operations performed through the existing admin Local Info editor UI** (`/content/local-info`, confirmed as one of 4 duplicate admin routes hitting the same tables — any one works; the plan uses `/content/local-info` since it's the first-listed and most directly named route), not code changes — except one small template check:

- **Delete "Safety & Health"**: delete the section row (cascades to its 3 items) via the admin editor's existing delete action.
- **Replace the emergency line value**: edit the "COY21 Emergency Line" item's `value` from `'TBC by Organising Team'` to the real text, formatted as requested: `Safeguarding Contact: Ayan Valizada — +994 997 36 83 33`, with the phone number wrapped in a real `tel:` link.
- **Add two Key Contacts items**: "Official Liaison Email" → `liaisons@climatecoy.com`, "COY21 Support Email" → `admin@climatecoy.com`, each with the email wrapped in a real `mailto:` link.

**Required code change:** `src/app/[locale]/(participant)/(shell)/local-info/page.tsx` currently renders every item's `value` as plain text (confirmed by reading the file — no link-detection exists). A small, generic helper (`linkifyContactValue`, in a new small file `src/lib/content/linkify-contact-value.ts`) detects a leading `tel:`/`mailto:`-style pattern embedded in the stored value and renders it as a real `<a>` tag; falls back to plain text for every other row (Water, Currency, Prayer times, Police, Ambulance, Fire, Registration Desk, etc. all stay plain text, unaffected). This keeps the data model simple (still one `text` column) while making exactly the 3 new/edited rows clickable, without turning every Local Info row into a link-parsing minefield. The exact embedded-link convention: the admin-entered value can optionally start with `tel:+994997368333 ` or `mailto:liaisons@climatecoy.com ` followed by the human-readable rest of the string; the helper strips the prefix, uses it as the `href`, and renders the full original string (prefix included or not, decided during implementation based on which reads better) as the link text. Decision deferred to implementation: simplest version is the helper looks for a `tel:` or `mailto:` URI anywhwere in the string via regex (`\b(tel:\+?[\d]+|mailto:[^\s]+)\b`) and wraps just that matched substring in a link, leaving the rest of the sentence as plain text around it — this needs no special data-entry convention at all beyond "paste the tel:/mailto: URI into the value field," which the plan's Task 3 testing step verifies works through the real admin UI.

### 6. Staff role narrowing: scanner + attendance only

**Current state (confirmed via research):** `isStaffRole` returns true for `staff` and `super_admin`; `is_staff()` SQL helper does the same; ~40+ RLS policies and 69+ application files gate on this single broad check across nearly every table and admin page.

**New state:** `staff` becomes scoped to exactly what `scanner_device` already has access to, **plus** the Admissions override/correction console (`/attendance/admissions`) and the Ops Dashboard (`/attendance/ops-dashboard`) — re-confirming against the request text: "(a) QR/Badge Scanner, (b) Attendance" is interpreted as the existing **Attendance nav group's scanning + attendance-taking surfaces**, i.e. `/attendance/scanners` (scanner-assignment management — note: the request says staff should not manage "anything" but a staff member taking attendance still needs to see which scanner they're assigned to; this page is read-oriented for a staff member viewing their own assignment, not broad scanner-fleet administration) is **excluded** per a strict reading of "QR/Badge Scanner, Attendance" as two capabilities, not five. **Final scope, confirmed narrow reading:**
- `/attendance/walk-in` (the actual QR/badge scan + walk-in admission flow) — kept.
- `/attendance/admissions` (attendance correction/override) — kept, since this is core "Attendance" capability, not a separate admin domain.
- `/attendance/scanners`, `/attendance/demand`, `/attendance/ops-dashboard` — **removed** from `staff` access (these are fleet-management/analytics, not "take attendance").
- Everything else (`/applications`, `/participants/*`, `/agenda/*`, `/allocation/*`, `/reports`, `/announcements`, `/staff`, `/staff/assignments`, `/settings`, `/content/local-info`, `/local-info-hub`, `/communications`) — **removed**.

This narrower reading is flagged explicitly for the user to confirm/adjust during spec review (see Open Questions) rather than silently assumed, since "Attendance" could reasonably be read to include `/attendance/scanners` too.

**Implementation layers (defense in depth, matching this codebase's existing established pattern of redundant checks). This section was substantially revised after spec review found real gaps in the original version — each fix below is cross-referenced against the reviewer's numbered findings:**

1. **New predicate**: add `src/lib/auth/staff-allowed-routes.ts` exporting `STAFF_ALLOWED_HREFS = ['/attendance/walk-in', '/attendance/admissions']` and `isRouteAllowedForStaff(role, pathname)` — `super_admin` always passes, `staff` only passes for an allowlisted href (prefix-matched, so `/attendance/admissions` also admits anything nested under it), every other non-participant role falls through unchanged. `isStaffRole` itself is **not** touched (staff must remain authenticatable as staff — only *where* staff can go is narrowed, not *whether* they're staff).

2. **Nav visibility**: `src/lib/nav/admin-nav-visibility.ts`'s `filterAdminNavGroups` changes from today's single all-or-nothing `isStaffRole` boolean (deliberately collapsed from a per-href table during the 2026-09-29 consolidation, per that migration's own doc comment) back to a per-href check **for `staff` specifically only** — every other role's visibility is completely unchanged. This is a partial, targeted reversal of last month's simplification, not a small filter tweak — the implementer should expect to reintroduce real per-href branching logic here, not just flip a boolean.

3. **Layout-level redirect — corrected per review finding #3**: `(admin)/layout.tsx`'s `decideAdminAccess` gates on `isNonParticipantRole`, NOT `isStaffRole` — it is deliberately wider and also admits `scanner_device`, after an earlier code-review fix that this spec must not regress. The staff-route-narrowing logic added here must explicitly branch only on `role === 'staff'` (using `isRouteAllowedForStaff` from layer 1), leaving every other non-participant role (`super_admin`, `scanner_device`) completely untouched by this new branch. Redirect target for a `staff` caller outside the allowlist: `/attendance/walk-in`.

4. **`/dashboard` and post-login landing — new, addresses review finding #5**: `resolvePostLoginDestination` currently sends every non-participant/non-scanner role (including `staff`) to `/dashboard` after login. `/dashboard` itself is gated by `isNonParticipantRole`, not `isStaffRole`, so narrowing `isStaffRole`/RLS alone does not stop staff from landing there — and once there, its cards/queries assume broad access. Fix: `resolvePostLoginDestination` gains a `role === 'staff'` branch sending staff directly to `/attendance/walk-in` instead of `/dashboard`, consistent with how `scanner_device` already gets its own dedicated landing page rather than the general admin dashboard. `decideAdminAccess`'s own narrowing (layer 3) still independently blocks a staff account that manually navigates to `/dashboard` by URL.

5. **`/participants/funding` — new, addresses review finding #5**: gated via `isFundingTypeStaffRole`/`canReadAttendanceConfirmation`, thin wrappers over `isStaffRole`, missed by the original route enumeration. Added to the "everything else — removed" list explicitly; covered automatically once layers 1-3 are in place (no separate code path needed beyond the allowlist check already covering every admin route via the layout).

6. **API routes — corrected per review finding #4, now a complete enumeration**: every admin-gated Route Handler needs the same `isRouteAllowedForStaff` check added directly, since API routes don't pass through `(admin)/layout.tsx`. Full list, confirmed by review (not just the original 2 the spec initially named):
   - `src/app/api/admit-walk-in/route.ts` — kept allowed (backs the one allowed scanner capability).
   - `src/app/api/admin/reports/participants-csv/route.ts` — returns 403 for `staff` (CSV export of all participants is not an attendance capability).
   - `src/app/api/admission-staff-health/route.ts` — returns 403 for `staff` (uses `requireAdmissionStaffCaller()`, same class as the CSV route — not an attendance capability).
   - `src/app/[locale]/(admin)/allocation/runs/[id]/export/route.ts` — returns 403 for `staff` (a Route Handler living inside the page-route tree, not under `src/app/api`, so it doesn't go through the admin layout either; backs the already-hidden Allocation feature, which staff must not retain API-level access to even though the UI is already hidden for everyone).

7. **Server Actions — addresses review finding #7. Revised again after round-2 review found the round-1 fix was itself too narrowly scoped (same vulnerability class, recurring one layer down).** Every Server Action in this codebase that performs a write using a **service-role client** (bypasses RLS entirely — the authorization check IS the app-layer role check, there is no RLS backstop for these) is a potential bypass once `staff`'s RLS/route/nav access is narrowed elsewhere, because none of those other layers touch a service-role-client write path. `requireStaffCaller()` is not the only helper with this exact shape, and is itself **not a single shared function** — confirmed by direct inspection: it is a locally-defined, duplicated, unexported function inside each of 2 files separately (`applications/[id]/actions.ts` has its own copy; `announcements/actions.ts` has its own, near-identical copy, with that file's own comment explicitly noting it's "not exported, matching this codebase's established [pattern]" of per-file local helpers rather than a shared import) — round 1's fix, by proposing to "patch `requireStaffCaller()`," implicitly assumed one shared definition and would have missed the second file's separate copy entirely if implemented literally. **Confirmed by direct enumeration** of every `require*Caller()`-style helper under `src/lib/*/server-helpers.ts` plus these 2 local duplicates, all of which delegate to `isStaffRole` (verified by reading each one's own role check, not assumed from the name):
   - `requireStaffCaller` — two separate local copies, both must be patched individually: `src/app/[locale]/(admin)/applications/[id]/actions.ts` (used by 3 actions: `updateApplicationStatus`, `assignReviewer`, `addNote`) and `src/app/[locale]/(admin)/announcements/actions.ts` (used by `createAnnouncement`).
   - `requireAdmissionStaffCaller` (`src/lib/admission/server-helpers.ts`) — backs the already-removed-from-staff admission-*review* workflow (distinct from the kept `/attendance/admissions` *attendance-correction* console below — same English word, two different features; do not conflate during implementation).
   - `requireAgendaStaffCaller` (`src/lib/agenda/server-helpers.ts`) — backs `/agenda/*`, already out of scope.
   - `requireFundingStaffCaller` / `requireAttendanceConfirmationReadCaller` (`src/lib/funding/server-helpers.ts`) — back `/participants/funding`, already out of scope (layer 5).
   - `requireImportStaffCaller` (`src/lib/import/server-helpers.ts`) — backs `/participants/import`, already out of scope.
   - `requireParticipantCareStaffCaller` (`src/lib/participant-care/server-helpers.ts`) — backs `/participants/care`, already out of scope.
   - `requireParticipantsCommunicationsStaffCaller` (`src/lib/participants-communications/server-helpers.ts`) — backs `/communications` (legacy, already unlinked), already out of scope.
   - `requireTravelOpsStaffCaller` (`src/lib/travel-ops/server-helpers.ts`) — backs `/participants/travel`, already out of scope.
   - `requireProgramAttendanceStaffCaller` (`src/lib/program-attendance/server-helpers.ts`) — **the one exception: this is the actual helper backing `/attendance/admissions`'s 6 exported actions (`performAdmitOverride`, `performCorrectAttendance`, `performTransferAttendance`, `searchApplicationsForAdmission`, `fetchAttendanceStateForApplication`, `fetchAttendanceAuditLog`), already enumerated exactly here rather than deferred** — this one must CONTINUE to pass `staff` through unchanged (it is the real implementation of the one console this spec keeps), while every other helper above must start rejecting `staff`.
   - (`requireScannerDeviceCaller`, `src/lib/scanner-device/server-helpers.ts`, is for the separate `scanner_device` role, not `staff` — explicitly out of scope for this layer, not touched.)

   **Remediation strategy — one chosen approach, not left as an either/or, and distinguishing the two different structural shapes found**: every helper is patched at its own `if (!isStaffRole(profile.role)) { ... }` role-check line (each file's own comment independently confirms this is "the single source of truth for this check" within that file) — changed from `isStaffRole(profile.role)` to `isStaffRole(profile.role) && profile.role !== 'staff'`, i.e. still admits `super_admin` (and any future broader role) but now unconditionally rejects `staff`. For the **7 real shared helpers** in `src/lib/*/server-helpers.ts` (every one listed above except `requireStaffCaller`, `requireProgramAttendanceStaffCaller`, and `requireScannerDeviceCaller`), patching the one shared definition is structurally sufficient — any Server Action calling one of these, present or added later, automatically inherits the fix. For **`requireStaffCaller` specifically**, which is NOT a shared function (confirmed: 2 separate local, unexported copies, one per file), **both copies must be patched individually** — this is not structurally future-proof against a third file adding its own third local copy of the same pattern the way the shared helpers are, so the implementation task explicitly re-runs `grep -rln "function requireStaffCaller" src/` (not just `requireStaffCaller(` usage) as a final check specifically for this one non-shared name, in addition to the general `require.*Caller` re-check layer 7 already calls for.
   - This list (8 helpers, their exact file paths, and the one correctly-kept exception) is the full, confirmed enumeration as of spec-review time — the implementation task still re-runs the equivalent search (e.g. `grep -rln "require.*Caller" src/lib --include="*.ts"`) at implementation time as a final completeness check before considering this layer done, in case a new helper was added between spec-writing and implementation, but it does **not** start from zero the way round 1's version did.

8. **RLS — the real enforcement boundary, corrected per review findings #1 and #2**: `is_staff()` is **not** redefined (`super_admin` logic depends on it meaning "staff OR super_admin" in places that must keep working). Add a new SQL helper `is_super_admin()` (`select current_user_role() = 'super_admin'`). A migration goes through the **complete, re-verified policy list** (not the original spec's undercount) replacing `is_staff()` with `is_super_admin()` on every policy **except** the confirmed attendance-domain surface, which keeps `is_staff()` unchanged:
   - **Keeps `is_staff()`** (staff retains access): `attendance_records`, `scan_attempts`, `scanner_assignments` RLS policies; `admit_walk_in` (backing `/attendance/walk-in`); and the exact RPCs reached transitively by `/attendance/admissions`'s 6 Server Actions (already enumerated precisely in layer 7 above via `requireProgramAttendanceStaffCaller`'s call sites — `performAdmitOverride`, `performCorrectAttendance`, `performTransferAttendance`, `searchApplicationsForAdmission`, `fetchAttendanceStateForApplication`, `fetchAttendanceAuditLog` — the implementation task reads each of these 6 functions' bodies to list their actual RPC/table calls, since this spec's research pass did not trace that deep; this is a smaller, well-bounded lookup, not an open-ended one).
   - **Converts to `is_super_admin()`** (staff loses access): every other policy currently on `is_staff()` from the 2026-09-29 consolidation migration (`supabase/migrations/20260929010000_consolidate_rls_policies_to_staff.sql`) and the inline-RPC-role-check migration (`20260929020000_consolidate_inline_role_checks_to_staff.sql`) — including, per review finding #1, two objects the original spec's table-level scan missed entirely: **`ops_dashboard_snapshot()`** and the **`ops_dashboard_broadcast_select` policy on `realtime.messages`** (both in `supabase/migrations/20261006071000_ops_dashboard_snapshot.sql`) — without this fix, a narrowed `staff` account could still call this RPC and read ops-dashboard realtime broadcasts directly, bypassing the UI/nav narrowing entirely, directly contradicting this spec's own stated intent that `/attendance/ops-dashboard` is out of scope for staff. Also covers the 2 `storage.objects` policies and any other non-table object (buckets, realtime) that review found the naive "grep for table names" approach would miss — the implementation task for this layer explicitly starts with `select * from pg_policies where qual ilike '%is_staff%' or with_check ilike '%is_staff%'` (or equivalent, run against the live linked project) to get the real, complete list before writing the migration, rather than reconstructing it from memory or a source-grep alone.

**Backfill:** no profile migration needed — `staff` stays the same enum value, only its RLS/route/Server-Action reach changes. Any existing `staff` row automatically gets the new narrower behavior the moment this migration applies; no per-row update required (there's no new column on `profiles`, the change is entirely in policy/application logic).

**Explicitly NOT in scope for this task** (confirmed via user's answer that no current staff needs broader access, and via the scope-boundary note above): reintroducing the 7 old per-domain roles, changing `super_admin`'s access at all, changing `scanner_device`'s access at all.

## Testing strategy

- Task 1 (My Profile fields): new unit tests for the `IdentityForm` client validation, a new live test (`tests/participant/my-profile-identity-live.test.ts`) proving the Server Action rejects missing fields and the avatar-upload/signed-URL round-trip works against the real Supabase Storage bucket.
- Task 2 (Accommodation validation): extend existing accommodation tests (if any exist — research didn't find a dedicated test file; one is added) proving the two now-required fields reject empty submission and `room_number` empty still saves successfully.
- Task 3 (Local Info content + linkify): a focused unit test for `linkifyContactValue` (pure function, easy to test in isolation: given a string with an embedded `tel:`/`mailto:` URI, returns the correctly split plain-text/link segments; given a string with neither, returns it unchanged).
- Task 4 (Staff narrowing): this is the task that most needs live-database proof, not just unit tests, since RLS is the real enforcement boundary.
