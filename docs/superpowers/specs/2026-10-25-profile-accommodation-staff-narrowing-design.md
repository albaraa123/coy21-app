# Profile Fields, Accommodation Requirements, Local Info Cleanup, and Staff Role Narrowing — Design

## Context

This is a 7-part change request from the user, covering several independent subsystems. Decomposed here into one combined spec (not split into separate sub-project specs) because 6 of the 7 items are small and share no meaningful complexity; only item 6 (Staff role narrowing) is large, and it's kept in this same spec because it's the dominant item and doesn't benefit from separate sequencing — everything here can land in one plan with clearly separated tasks.

A pre-implementation research pass (via a research subagent) established the following, which changes the shape of several items from how the original request assumed them:

- **"My Profile" currently has no name/email/phone/photo fields at all.** It only contains Emergency Contacts and Accommodation forms. `profiles.full_name`/`profiles.email` are set once at signup (via the `handle_new_user()` trigger) and have never been user-editable anywhere in this codebase. No profile-picture/avatar column or UI exists anywhere.
- **Accommodation is a real, existing form** (`application_accommodation` table: `hotel_name`, `room_number`, `location_note`, all nullable) with zero validation today, client or server.
- **"Safety & Health" is not a dedicated page/route.** It's one content section (with 3 items: Water, Currency, Prayer times) inside the generic, database-driven "Local Info Hub" feature, which participants see post-login at `/local-info`. Deleting it is a data operation, not a code deletion.
- **The emergency-line text "COY21 Emergency Line +90 555 000 1111" does not exist anywhere in the codebase.** The real current value is a placeholder: `local_info_items` row with `label = 'COY21 Emergency Line'`, `value = 'TBC by Organising Team'`, inside a separate "Emergency Numbers" section (siblings: Police, Ambulance, Fire). This is the row to update.
- **"Key Contacts" already exists** as another Local Info Hub section (Registration Desk, Info Desk, Medical Point, Lost & Found). The two new email contacts are added as two more items in this same section, visible to participants post-login — confirmed with the user this is the intended audience (not the pre-login public Contact page).
- **The `staff` role was deliberately broadened to near-total system access exactly one month before this request** (2026-09-29 "staff role consolidation" — see `docs/superpowers/specs/2026-09-29-staff-role-consolidation-design.md`), collapsing 7 narrow domain roles into one. This request reverses that decision for `staff` specifically. Confirmed with the user: no currently-active staff account needs anything beyond scanning/attendance today, so this is a straight redefinition of what `staff` means, not a resurrection of the old 7 sub-roles. `super_admin` is unaffected and continues to have full access.

## Scope boundaries (explicitly confirmed, not to be second-guessed during implementation)

- Items 3/4/5 (Local Info content) are **data edits via the existing admin Local Info editor**, not new code, except where the rendering template needs `tel:`/`mailto:` link support added (checked in Task 1 below).
- Item 1 adds 4 **new** fields to My Profile (name, email, phone, profile picture) — this is new feature work, not a validation tweak on existing fields.
- Item 2 adds validation to the **existing** 3 accommodation fields; `room_number` is explicitly exempt.
- Item 6 redefines `staff`'s own RLS/route access down to scanner + attendance only. It does **not** reintroduce the old 7 sub-roles. It does **not** change `super_admin`.
- `scanner_device` (the existing, separate, narrow role used for dedicated kiosk/scanner-only devices) is the access-shape template for the new narrow `staff`, but `staff` and `scanner_device` remain **distinct roles** — `staff` is a human staff member's personal login (lands on a shell with their name, not the bare kiosk `/scanner` UI), scoped to exactly the same two capabilities (scan QR, view/manage attendance), not merged into `scanner_device` itself.

## Design

### 1. My Profile: add Name, Email, Phone, Profile Picture (required)

**Where:** `src/app/[locale]/(participant)/(shell)/my-profile/page.tsx` and `profile-forms.tsx` gain a new `IdentityForm` section, rendered above the existing Emergency Contacts / Accommodation forms.

**Fields and storage:**
- **Name** → `profiles.full_name` (already exists, `not null`, currently never user-edited — this is the first feature to make it editable).
- **Email** → `profiles.email` (already exists, `not null`). Editing a user's auth email is a real identity change in Supabase Auth, not just a `profiles` row update — changing it must go through `supabase.auth.updateUser({ email })`, which triggers Supabase's own confirmation-email flow (the email doesn't change until the user clicks the confirmation link). The `profiles.email` row stays in sync via the existing `handle_new_user`-style trigger pattern only at signup; for an edit, the Server Action must explicitly update both `auth.users.email` (via the user's own session, which is what `auth.updateUser` does) and leave `profiles.email` to be updated by a new trigger on `auth.users` email change (simpler and more consistent than having the Server Action write `profiles.email` directly, which would desync from the pending/unconfirmed auth email). **Decision: add a lightweight `on update of email on auth.users` trigger** that syncs `profiles.email` only after Supabase confirms the new email (i.e., trigger fires on the real `auth.users.email` change, which Supabase only applies post-confirmation) — this avoids ever showing a "confirmed" email in `profiles` before the user actually confirms it.
- **Phone** → new column `profiles.phone text`. (Not reusing `applications.phone`, which is a point-in-time application-snapshot field, deliberately separate per the existing schema comment — confirmed in research. A profile phone is the current, editable identity field.)
- **Profile Picture** → new column `profiles.avatar_path text` (storage object path, nullable) + a new private Supabase Storage bucket `avatars`, one file per user keyed by `auth.uid()`, RLS-scoped so a user can only read/write their own. Displayed via a signed URL generated server-side (avoids making the bucket public). Required field, but "required" for an *already-uploaded* picture means: the form blocks save only if no picture has ever been uploaded (first-time save must include one); re-saving other fields without re-uploading a picture that's already on file is fine, since the picture doesn't need to be re-attached on every save.

**Validation (client):** `IdentityForm` in `profile-forms.tsx` follows the established `requiredFieldsError` pattern (same as the 6 admin "New X" managers) — `.trim()` checks on name/email/phone, checks `avatarPath` is set (either previously-saved or newly-selected-this-session) before allowing save, single `t('requiredFieldsError')` banner on failure. A `*` suffix is added next to each of the 4 field labels.

**Validation (server):** the Server Action (`saveIdentity` in `actions.ts`) independently re-validates all 4 fields are non-empty/non-whitespace (and that an avatar path exists) before writing anything — rejecting with a clear error if not, matching the pattern the research found was *missing* from the existing Emergency Contacts/Accommodation actions. This is the first Server Action in this feature area to add real server-side required-field enforcement; Emergency Contacts/Accommodation are left as they are (out of scope — not part of this CR).

**DB constraint:** `profiles.phone` and `profiles.avatar_path` added as nullable columns (a hard `NOT NULL` constraint is not used, to avoid breaking any existing profile row created before this feature — enforcement is at the application layer, consistent with how every other "required" field in this codebase, e.g. the admin manager forms, is enforced only at the app layer, not the DB layer).

### 2. Accommodation: require hotel_name and location_note, keep room_number optional

**Where:** `profile-forms.tsx`'s existing `AccommodationForm`, `actions.ts`'s existing `saveAccommodation`.

**Client:** add a `.trim()` required check on `hotel_name` and `location_note` only (not `room_number`), `t('requiredFieldsError')` banner, `*` marker on the two required field labels (not on Room Number's label).

**Server:** `saveAccommodation` gains the same two-field required check, rejecting before the Supabase write if either is missing — this closes the real gap research found (no server-side validation existed at all for this form).

**DB:** no migration needed — `hotel_name`/`location_note` stay nullable at the DB level (same reasoning as Task 1's identity fields: app-layer enforcement, not a DB constraint, consistent with this codebase's existing pattern).

### 3/4/5. Local Info Hub content changes

All three are **data operations performed through the existing admin Local Info editor UI** (`/content/local-info`, confirmed as one of 4 duplicate admin routes hitting the same tables — any one works; the plan uses `/content/local-info` since it's the first-listed and most directly named route), not code changes — except one small template check:

- **Delete "Safety & Health"**: delete the section row (cascades to its 3 items) via the admin editor's existing delete action.
- **Replace the emergency line value**: edit the "COY21 Emergency Line" item's `value` from `'TBC by Organising Team'` to the real text, formatted as requested: `Safeguarding Contact: Ayan Valizada — +994 997 36 83 33`, with the phone number wrapped in a real `tel:` link.
- **Add two Key Contacts items**: "Official Liaison Email" → `liaisons@climatecoy.com`, "COY21 Support Email" → `admin@climatecoy.com`, each with the email wrapped in a real `mailto:` link.

**Required code change:** `src/app/[locale]/(participant)/(shell)/local-info/page.tsx` currently renders every item's `value` as plain text (confirmed by reading the file — no link-detection exists). A small, generic helper (`linkifyContactValue`, in a new small file `src/lib/content/linkify-contact-value.ts`) detects a leading `tel:`/`mailto:`-style pattern embedded in the stored value and renders it as a real `<a>` tag; falls back to plain text for every other row (Water, Currency, Prayer times, Police, Ambulance, Fire, Registration Desk, etc. all stay plain text, unaffected). This keeps the data model simple (still one `text` column) while making exactly the 3 new/edited rows clickable, without turning every Local Info row into a link-parsing minefield. The exact embedded-link convention: the admin-entered value can optionally start with `tel:+994997368333 ` or `mailto:liaisons@climatecoy.com ` followed by the human-readable rest of the string; the helper strips the prefix, uses it as the `href`, and renders the full original string (prefix included or not, decided during implementation based on which reads better) as the link text. Decision deferred to implementation: simplest version is the helper looks for a `tel:` or `mailto:` URI anywhwere in the string via regex (`\b(tel:\+?[\d]+|mailto:[^\s]+)\b`) and wraps just that matched substring in a link, leaving the rest of the sentence as plain text around it — this needs no special data-entry convention at all beyond "paste the tel:/mailto: URI into the value field," which the plan's Task 3 testing step verifies works through the real admin UI.

### 6. Staff role narrowing: scanner + attendance only

**Current state (confirmed via research):** `isStaffRole` returns true for `staff` and `super_admin`; `is_staff()` SQL helper does the same; ~40+ RLS policies and 69+ application files gate on this single broad check across nearly every table and admin page.

**New state:** `staff` becomes scoped to exactly what `scanner_device` already has access to, **plus** the Admissions override/correction console (`/attendance/admissions`) and the Ops Dashboard (`/attendance/ops-dashboard`) — re-confirming against the request text: "(a) QR/Badge Scanner, (b) Attendance" is interpreted as the existing **Attendance nav group's scanning + attendance-taking surfaces**, i.e. `/attendance/scanners` (scanner-assignment management — note: the request says staff should not manage "anything" but a staff member taking attendance still needs to see which scanner they're assigned to; this page is read-oriented for a staff member viewing their own assignment, not broad scanner-fleet administration) is **excluded** per a strict reading of "QR/Badge Scanner, Attendance" as two capabilities, not five. **Final scope, confirmed narrow reading:**
- `/attendance/walk-in` (the actual QR/badge scan + walk-in admission flow) — kept.
- `/attendance/admissions` (attendance correction/override) — kept, since this is core "Attendance" capability, not a separate admin domain.
- `/attendance/scanners`, `/attendance/demand`, `/attendance/ops-dashboard` — **removed** from `staff` access (these are fleet-management/analytics, not "take attendance").
- Everything else (`/applications`, `/participants/*`, `/agenda/*`, `/allocation/*`, `/reports`, `/announcements`, `/staff`, `/staff/assignments`, `/settings`, `/content/local-info`, `/local-info-hub`, `/communications`) — **removed**.

This narrower reading is flagged explicitly for the user to confirm/adjust during spec review (see Open Questions) rather than silently assumed, since "Attendance" could reasonably be read to include `/attendance/scanners` too.

**Implementation layers (defense in depth, matching this codebase's existing established pattern of redundant checks):**

1. **New predicate**: `src/lib/auth/is-staff-role.ts` gains a narrower, explicit `STAFF_ALLOWED_HREFS` or equivalent — actually, cleaner: introduce `isNarrowStaffRole(role)` is the wrong shape (staff is still staff, just restricted by *route*, not by a different role check). Correct shape: keep `isStaffRole` as-is for *authentication purposes* (staff is still "staff", distinct from a participant), but add a new `src/lib/auth/staff-allowed-routes.ts` exporting a `STAFF_ALLOWED_HREFS` allowlist (`['/attendance/walk-in', '/attendance/admissions']`) and a helper `isRouteAllowedForStaff(role, pathname)` — `super_admin` always passes, `staff` only passes for an allowlisted href, every other non-participant role falls through to existing behavior unchanged.
2. **Nav visibility**: `src/lib/nav/admin-nav-visibility.ts`'s `filterAdminNavGroups` is updated so that for `role === 'staff'` specifically, only nav items whose href is in `STAFF_ALLOWED_HREFS` survive the filter (every other role keeps today's behavior — this only narrows `staff`, it does not change `super_admin` or any other role's visibility).
3. **Page-level redirect**: every admin page currently gated by a bare `isStaffRole(profile.role)` check needs to additionally confirm, for `staff` specifically, that the current route is in the allowlist — redirecting (not just hiding nav) to `/attendance/walk-in` if not. Rather than hand-edit 69+ files, this is centralized: `(admin)/layout.tsx`'s existing `decideAdminAccess` (the single chokepoint every admin route already passes through, confirmed in research as already handling the broader "is this role allowed into /admin at all" check) gains the additional per-route narrowing for `staff`, redirecting server-side before any page body renders — this means individual page files do NOT need to be touched one-by-one, since they all already render inside this layout.
4. **API routes**: `src/app/api/admit-walk-in/route.ts` and any other admin-only API route need the same allowlist check added directly (API routes don't go through the admin layout). Research found `src/app/api/admin/reports/participants-csv/route.ts` as the only other admin-gated API route — this one explicitly returns 403 for `staff` (CSV export of all participants is not an attendance capability).
5. **RLS**: this is the real enforcement boundary, independent of application code. `is_staff()` is **not** redefined (it's used by `super_admin` logic too, and many policies correctly want "staff OR super_admin"). Instead, every RLS policy currently granting `staff` (via `is_staff()`) access to a table **outside** attendance's scope needs a new, narrower policy shape. Given the 2026-09-29 consolidation collapsed ~40 policies onto `is_staff()`, and this request only wants to narrow `staff` (not `super_admin`), the correct fix is: **keep `is_staff()` as "staff OR super_admin" for `super_admin`'s sake, but gate every non-attendance policy on `is_staff() AND auth_user_role() != 'staff'` is wrong (excludes staff from things super_admin still needs) — actually correct approach: split into `is_super_admin_or_staff()` kept only on attendance-domain tables, and every other table's policy changes from `is_staff()` to a new `is_super_admin()` -only check.** This is the cleanest, smallest-surface-area fix: one new SQL helper `is_super_admin()` (`select current_user_role() = 'super_admin'`), and a migration that goes table-by-table through the 2026-09-29 consolidation migration's own policy list, replacing `is_staff()` with `is_super_admin()` everywhere **except** the attendance-domain tables (`attendance_records`, `scan_attempts`, `scanner_assignments`, and the specific RPCs backing walk-in admission/admission-review that `staff` must still call) which keep `is_staff()` (still means "staff OR super_admin", correctly scoped to the one domain `staff` retains).

**Backfill:** no profile migration needed — `staff` stays the same enum value, only its RLS/route reach changes. Any existing `staff` row automatically gets the new narrower behavior the moment this migration applies; no per-row update required (this differs from a typical "backfill a new column" migration — there's no new column on `profiles`, the change is entirely in policy/application logic).

**Explicitly NOT in scope for this task** (confirmed via user's answer that no current staff needs broader access, and via the scope-boundary note above): reintroducing the 7 old per-domain roles, changing `super_admin`'s access at all, changing `scanner_device`'s access at all.

## Testing strategy

- Task 1 (My Profile fields): new unit tests for the `IdentityForm` client validation, a new live test (`tests/participant/my-profile-identity-live.test.ts`) proving the Server Action rejects missing fields and the avatar-upload/signed-URL round-trip works against the real Supabase Storage bucket.
- Task 2 (Accommodation validation): extend existing accommodation tests (if any exist — research didn't find a dedicated test file; one is added) proving the two now-required fields reject empty submission and `room_number` empty still saves successfully.
- Task 3 (Local Info content + linkify): a focused unit test for `linkifyContactValue` (pure function, easy to test in isolation: given a string with an embedded `tel:`/`mailto:` URI, returns the correctly split plain-text/link segments; given a string with neither, returns it unchanged).
- Task 4 (Staff narrowing): this is the task that most needs live-database proof, not just unit tests, since RLS is the real enforcement boundary. New live test `tests/auth/staff-narrow-access-live.test.ts` proves, against the real linked project: a real `staff`-role test account can still call the walk-in/admissions RPCs and read/write `attendance_records`/`scan_attempts`, and is independently confirmed REJECTED (RLS-level, not just app-level) when attempting to read `applications`, `application_travel_info`, `sessions`, or any other now-out-of-scope table directly. The existing `tests/auth/staff-roles-live.test.ts` and the 18 files research found referencing `'staff'` role behavior are read task-by-task during implementation and updated wherever they assert the old, now-incorrect broad-access behavior — this is the task most likely to surface test breakage, matching this session's own prior experience fixing `@test.local` fixture issues, so each affected test file is updated deliberately, not blanket-patched.

## Open questions — resolved with the user before plan-writing

1. **Staff's exact allowed-route scope** — CONFIRMED: `/attendance/walk-in` + `/attendance/admissions` only. `/attendance/scanners`, `/attendance/demand`, `/attendance/ops-dashboard` are excluded from `staff` access, as the design above already assumed.
2. **Profile picture requirement for already-registered participants** — CONFIRMED: required only for the first save (no avatar on file at all yet). An existing participant with no avatar can still save an edit to another field (e.g. phone number) without being forced to upload a photo in that same save, as the design above already assumed.

Both answers match the design as already written above — no changes needed to the Design section as a result.
