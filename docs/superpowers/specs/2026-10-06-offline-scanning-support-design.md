# Offline Scanning Support (5b) — Design Spec

Sub-project 5b of the 6-part COY21 platform decomposition. Depends on nothing merged after 5a (live operations dashboard, merged to `master`). Deferred from 5a's scope explicitly — see `docs/superpowers/specs/2026-10-05-ops-dashboard-design.md`'s Out of Scope section.

## Problem

The scanner app (`src/components/scanner/scanner-client.tsx`) is currently strictly online-only: `use-network-status.ts` wraps `navigator.onLine` and the browser's `online`/`offline` events, and the client short-circuits every submit attempt while offline — it never even calls the server. A failed network call is bucketed into a three-way taxonomy (`offline-blocked`, `uncertain`, `server`) purely for operator-facing messaging; there is no retry, no queue, no persistence of any kind.

The walk-in admission page (`src/app/[locale]/(admin)/attendance/walk-in/`) has no network-status awareness at all today — no offline detection, no retry, nothing. It's a separate admin page (staff-only, `requireAdmissionStaffCaller`), not part of the scanner flow, and is addressed as its own track below rather than conflated with the scanner.

One prior spec (`2026-07-31-flexible-admission-qr-attendance-design.md`, lines 17, 298, 347) flagged offline behavior as a known, explicitly deferred gap, anticipating a future "PWA offline-queue/sync" follow-up spec, and established one hard constraint any such design must preserve: **no local "optimistic" admission that could double-book on reconnect.** That source does not itself forbid a queue — it only forbids a queue (or any design) making a local admission decision the server hasn't confirmed. This spec's choice to build auto-retry instead of a queue is **this spec's own scope decision**, made because a queue gains nothing here (see Scope Decision below), not something the earlier spec mandates.

**The actual failure modes, verified against current code, are asymmetric between the two admission paths:**

- **QR path**: a naive retry after a lost response already resolves safely today. `scan_attempt_transactional` is idempotent in effect — a retried scan of an already-admitted ticket returns `result: 'duplicate'`, which `result-presentation.ts` renders as `severity: 'attention'` ("informational, not an error — they're already in"), not a rejection. Idempotency keys for this path are a UX/efficiency improvement (skip re-running the full decision tree, restore the original `admitted`/`flexible_admitted` result and participant summary instead of a generic `duplicate`), not a correctness fix for a false rejection.
- **Walk-in path**: a naive retry after a lost success genuinely produces a false rejection today. `admit_walk_in`'s pre-insert check (`'This participant already has a booking for this session'`) fires before reaching any uniqueness constraint, so a retried walk-in of an already-admitted participant raises a hard error with no idempotent fallback. **This is the one genuine correctness bug this spec exists to fix**, and the walk-in design below must close it precisely.

## Scope Decision

**Build:** client-side auto-retry for both the scanner and the walk-in admin page, each on top of its own existing architecture, protected by server-side idempotency keys so a lost response can never produce a wrong outcome (double-admission, or — walk-in specifically — a false rejection of an already-admitted participant).

**Do not build:** any offline queue, any local admission decision, any "pending sync" state visible to the operator, any change to the PWA shell (`manifest.ts`, `sw.js`, `install-guidance.tsx` stay untouched — those remain scoped to static-asset caching/installability per their own existing comments).

## Architecture — Server Side

### Two independent idempotency mechanisms, on the tables each function actually writes to

- **QR scan path**: `scan_attempt_transactional` (the function that actually performs every insert — `scan_qr_attempt_transactional` is a thin bridge that delegates to it, see Signature Changes below) inserts exactly one `scan_attempts` row per call in the common case, but has two exception paths that insert nothing at all (advisory-lock-exhausted at line 142-144 of `20261006050000_walk_in_admission.sql`, and scanner-scope-revoked at line 160-162) — both `raise exception`, propagating as a thrown error. Gets `scan_attempts.idempotency_key` (`uuid`, nullable, unique index) plus `scan_attempts.scan_fingerprint` (`bytea`, nullable — a derived fingerprint, not the raw credential hash; see Column Content below).
- **Walk-in path**: `admit_walk_in` writes to `session_bookings` and `attendance_records`, returns only a `booking_id` (`uuid`). Gets `session_bookings.idempotency_key` (`uuid`, nullable, unique index).

Both keys are nullable so existing rows and existing callers (the override path in `src/lib/attendance/admission-management.ts`, and `src/lib/attendance/scan-attempt.ts`'s non-QR scan path) are completely unaffected — every new parameter defaults to `null`, and a `null` key means "skip the idempotency check entirely, behave exactly as today." Postgres's unique index semantics (distinct `NULL`s never conflict) mean this requires no backfill and no behavior change for any caller that doesn't pass a key.

### Idempotency check placement — AFTER auth, AFTER the serialization point, not "at the very top"

This is the one point both admission functions must get right, and it differs by function because their serialization mechanisms differ:

**`admit_walk_in`** (current body: `20261006052000_admit_walk_in_shared_advisory_lock.sql`):
1. `is_staff()` check (line 41) — unchanged, runs first. An idempotency lookup must never run before authorization; returning a cached `booking_id` to an unauthorized caller would be a privilege leak.
2. Application-accepted check (line 45) — unchanged.
3. `select ... for update` on `sessions` (line 49) — unchanged.
4. **New: idempotency key check goes here, immediately after the advisory lock (line 61) and before the capacity/duplicate-booking checks (line 71-89).** This is the fix for the race the naive design misses: if the key check only happened via a `unique_violation` catch around the final `session_bookings` insert (line 91-93), a concurrent retry with the same key would reach the pre-insert `'already has a booking'` check (line 77-82) first — once the original request has committed, that check fires and raises the exact false rejection this spec exists to prevent, never reaching the insert at all. Checking immediately after the lock means every retry with the same key sees the first request's committed row (under READ COMMITTED, once serialized by the lock) and returns it directly, never reaching the business checks that would misfire.
5. If a matching key exists: compare `application_id`+`session_id` against the stored row's. Match → return the stored `booking_id` immediately. Mismatch → raise `'Idempotency key reused with different admission data'`.
6. If no matching key: proceed with existing logic unchanged, write the key into the final `session_bookings` insert.
7. **Race backstop**: wrap the `session_bookings` insert in `begin...exception when unique_violation`, but — same caveat as the QR path below — `session_bookings_active_unique` (`20260823020000_session_bookings.sql`) is a second, unrelated constraint on this same table that can also legitimately raise `unique_violation` for a real conflict unrelated to key reuse. Use `get stacked diagnostics` to check `constraint_name` and branch three ways, not two: (a) violated constraint is `session_bookings_active_unique` → `raise;` unchanged, a real conflict; (b) violated constraint is the new `idempotency_key` unique index AND re-fetching the row that won the race shows its `application_id`/`session_id` match this call's own → re-fetch-and-return that `booking_id`, the legitimate same-operation-retry case; (c) violated constraint is the idempotency index but the winning row's `application_id`/`session_id` does NOT match → raise the SAME `'Idempotency key reused with different admission data'` mismatch error step 5 raises, never silently hand back a different request's `booking_id` just because the backstop fired instead of the primary check. (The only way to reach case (c) is the same key reused across two different sessions/applications racing before either's lock serializes them — vanishingly unlikely given the `for update` below, but the backstop must not quietly do the wrong thing if it ever happens.) The serialization point is actually the `select ... for update` on `sessions` (line 49, not the advisory lock at line 61 — a second same-key caller for the SAME session blocks there, not at the lock, since `for update` itself serializes against another in-progress transaction touching the same session row); this backstop is pure defense in depth for the already-closed same-session race, and the real-world case it's actually reachable for is the cross-session one in branch (c).

**`scan_attempt_transactional`** (current body: `20261006050000_walk_in_admission.sql` lines 101-266):
1. Advisory lock acquisition loop (lines 135-144) — unchanged. If lock acquisition fails after retries, this raises an exception with no insert at all; a client-side retry of the *whole attempt* (not just the idempotency wrapper) is the correct response, since nothing was recorded (see Client-Side Error Classification below — this is a retryable error).
2. Scanner-scope re-check (lines 152-163) — unchanged, runs with the lock held. If scope was revoked, this raises `'Not authorized for this session/room'` with no insert. **Decision: the idempotency check runs AFTER this scope re-check, not before.** Rationale: replaying a completed admission to a scanner whose assignment was just revoked mid-shift should still surface the auth failure on retry attempts after revocation, not silently hand back a stale success — the scope check protects a real-time security boundary, and an idempotent replay must not bypass it.
3. **New: idempotency key check goes here**, immediately after the scope re-check, before the application/session lookup (line 165) and before any part of the admission-decision tree.
4. If a matching key exists: compare the stored row's `scan_fingerprint` against the incoming fingerprint using `is not distinct from` (not `=` — see Mismatch Check Details below, this handles the malformed/unresolved-credential branches where the fingerprint input is legitimately `null`-derived), AND compare `session_id`. Match on both → return the stored row immediately (no re-execution of the decision tree, no second `attendance_records` insert). Mismatch on either → raise `'Idempotency key reused with different scan data'`.
5. If no matching key: proceed with existing logic completely unchanged through the full decision tree (lines 165-258).
6. **The final insert at lines 260-262 is the only place the key is written.** The idempotency check in step 4 runs while the per-session advisory lock (acquired in step 1, held until the transaction ends) is still held, so a second caller with the same key — necessarily targeting the same session, since the check also compares `session_id` — cannot even begin executing until the first caller's transaction has fully committed and released the lock. By the time the second caller's key check runs, it is a fresh statement under READ COMMITTED and sees the first caller's committed row directly. The second caller never reaches the decision tree at all; there is no window for it to compute an independent decision or insert a second `attendance_records` row for the SAME session.
   - **`unique_violation` backstop must wrap BOTH inserts, not just the final one** — review correctly caught that wrapping only `scan_attempts`'s insert (lines 260-262) leaves the `attendance_records` insert (lines 255-257, which runs first and unconditionally for an admitting result) outside any exception handler. If that `attendance_records` insert itself succeeds and only the subsequent `scan_attempts` insert then hits a cross-session key collision, the backstop's exception handler fires with a real, committed `attendance_records` row already in place and no matching `scan_attempts` row — an orphaned admission. **Fix: wrap lines 246-262 (the entire admitting branch's insert sequence) in one `begin...exception when unique_violation` block**, so that if the `scan_attempts` insert at the end fails, the whole block (including the just-attempted `attendance_records` insert) is rolled back as a single unit before the exception handler runs its recovery logic.
   - Inside that handler, branch three ways on `constraint_name` via `get stacked diagnostics`, same logic as the walk-in path above: (a) `attendance_records_no_duplicate_active` → `raise;` unchanged, a real conflict unrelated to key reuse; (b) the idempotency index, and the winning `scan_attempts` row's `scan_fingerprint`/`session_id` match this call's own → re-fetch-and-return that row; (c) the idempotency index, but the stored row's fingerprint/session do NOT match → raise the same `'Idempotency key reused with different scan data'` mismatch error step 4 raises, never silently return a different request's row. The per-session advisory lock makes same-session collisions here effectively unreachable (step 4's check already catches those); the real-world case this backstop handles is branch (c), a cross-session key reuse — a client bug, not a legitimate retry.
7. **The two unresolved-credential early-return branches in `scan_qr_attempt_transactional`** (malformed hash, no active credential match — lines 291-306 of the file, which insert directly rather than delegating to `scan_attempt_transactional`) need their own, independent idempotency check and insert, since they never reach `scan_attempt_transactional`'s lock at all. They take no advisory lock today and don't need one added — each is a single, unconditional insert, so the insert-level `unique_violation` catch alone is sufficient there (no decision tree to protect from double-execution, since there is no decision — it's an unconditional `invalid_qr`), with the same constraint-name branching as step 6 above.

### Signature changes

- `scan_attempt_transactional(p_application_id, p_session_id, p_scanned_by, p_device_identifier, p_time_slot_group_key, p_is_override_caller default false, p_scanner_user_id default null, p_idempotency_key uuid default null, p_token_hash bytea default null)` — two new trailing optional parameters, both defaulting to `null`. `p_token_hash` is accepted here (not only in the wrapper) because the idempotency check and the final insert both need it, and both live in this function per the placement rules above.
- `scan_qr_attempt_transactional(..., p_idempotency_key uuid default null)` — one new trailing parameter, forwarded straight through to `scan_attempt_transactional` alongside the `p_token_hash` it already has from its own existing parameter list. Its own two unresolved-credential branches use `p_idempotency_key` directly for their own independent check (point 7 above).
- `admit_walk_in(p_application_id, p_session_id, p_idempotency_key uuid default null)` — one new trailing parameter.
- Every signature change needs: `drop function if exists` on the old arity (matching this codebase's established precedent in `20261006050000_walk_in_admission.sql` lines 98-99), the full `revoke`/`grant` restatement these functions already carry, and regenerating `src/types/database.ts` afterward.
- **Security fix riding along with `admit_walk_in`'s signature change, found during spec review — `admit_walk_in` has never had `PUBLIC`'s default `EXECUTE` revoked.** `20261006050000_walk_in_admission.sql` line 86 only ever adds `grant execute ... to authenticated`; no migration anywhere revokes the default `EXECUTE` Postgres grants every new function to `PUBLIC`. Combined with `is_staff()`'s own documented NULL-for-anonymous-caller behavior (`select current_user_role() in (...)`, which returns `NULL` rather than `false` when `auth.uid()` has no matching `profiles` row — see this project's own `is_staff_null_bypass_pattern` precedent, where `ops_dashboard_snapshot()` had the identical bug: `if not is_staff()` evaluates `if not NULL`, which is never true, so the exception never fires for an anonymous/profile-less caller), `admit_walk_in` is a second, independent instance of a vulnerability already found and fixed once in this codebase. Since this spec already drops and recreates this function for its new parameter, the fix belongs in that same migration rather than deferred: change line 41's bare `if not is_staff()` to `if not coalesce(is_staff(), false)`, and add `revoke execute on function admit_walk_in(uuid, uuid, uuid) from public;` immediately after the new `grant`. Verify the fix the same way the `ops_dashboard_snapshot()` fix was verified live: `select has_function_privilege('anon', 'admit_walk_in(uuid,uuid,uuid)', 'execute')` must return `false` after this migration lands, and an anon-key RPC call to `admit_walk_in` must fail with a permission error, not reach the function body at all.
- **Existing callers unaffected**: `src/lib/attendance/scan-attempt.ts`'s direct (non-QR) scan path, and `src/lib/attendance/admission-management.ts`'s override-admission path, both call `scan_attempt_transactional` without the new parameters today and must continue to compile/work unchanged — passing `null` for both new parameters is the default, so no call-site change is required there. This sub-project touches only `scan-qr-attempt.ts`'s call site and the walk-in action.

### Mismatch check details

- Use `is not distinct from` for the stored `scan_fingerprint` comparison, never `=` — the malformed-payload branch passes `p_token_hash = null` today (`scan-qr-attempt.ts`), which feeds into a fingerprint computed from a `null` input, and `null = null` evaluates to `null` (neither true nor false) in SQL — comparing two such fingerprints under plain `=` would incorrectly fail a legitimate retry of a malformed-payload scan. `is not distinct from` treats equal fingerprints (including two both derived from `null`) as equal, exactly as intended.
- The comparison must include `session_id` as well as the fingerprint/`application_id` — a client bug that reuses a key across two different sessions is exactly the kind of misuse this check exists to catch, which the fingerprint alone wouldn't detect (it's already derived including `session_id`, per the Column Content section below, but the check should compare `session_id` explicitly too for clarity rather than relying solely on the fingerprint's own construction).

### Column content — `scan_attempts.scan_fingerprint` is a derived fingerprint, not the raw credential hash

`scan_attempts` already has broader read access than `qr_credentials` (`scan_attempts_scanner_select`/staff policies grant read access to scanner-device and staff roles; `qr_credentials` access is far narrower). Storing the raw `token_hash` value on every `scan_attempts` row would copy credential-lookup material into a more widely readable table purely for an idempotency-mismatch check that doesn't need the real hash — it only needs *something* that changes if the QR changes. Store a derived fingerprint instead, under a column named `scan_fingerprint bytea` (not `token_hash` — that name would misleadingly imply the real credential hash is stored):

```sql
extensions.digest(coalesce(p_token_hash, ''::bytea) || uuid_send(p_session_id), 'sha256')
```

Two details this exact expression exists to get right, both found during spec review against the real schema:
- **Schema-qualify `digest()` as `extensions.digest(...)`, never bare `digest(...)`.** `scan_attempt_transactional` runs under a hardened `set search_path = public, pg_temp` (no `extensions`, where pgcrypto is installed on this Supabase project). This exact mistake already happened once in this codebase's history — `admit_walk_in` hit `SQLSTATE 42883: function digest(text, unknown) does not exist` for precisely this reason, fixed in `20261006051000_fix_admit_walk_in_search_path.sql`. Schema-qualifying the call avoids needing to widen this function's own search_path.
- **Concatenate as `bytea`, never mix in a bare `::text` cast.** `p_session_id::text` concatenated directly against a `bytea` with `||` has no implicit cast in either direction; Postgres resolves it via the generic `anynonarray || text` operator, producing a *text* value (the bytea's `\x`-prefixed printed representation, concatenated with the uuid string) rather than a byte sequence — which would make the fingerprint's actual value depend on the session's `bytea_output` setting, a dependency with no reason to exist here. `uuid_send(p_session_id)` returns the uuid's raw 16-byte form directly, keeping the whole expression `bytea` throughout with no cast-dependent behavior.

Computed the same way in both the malformed-payload/unresolved-credential branches and the resolved-credential branch. Because of the `coalesce`, this expression is never itself `null` — the `is not distinct from` comparison in Mismatch Check Details above is harmless to keep regardless, but the NULL-safety concern it was originally written to address doesn't actually arise once this `coalesce` is in place.

## Architecture — Client Side (Scanner)

### Platform constraint: Next.js Server Actions dispatched from one client are processed one at a time

This governs the whole client design below and must be designed around, not discovered mid-implementation: Next.js serializes Server Actions dispatched from the same client — confirmed directly against this project's installed Next 16.2.11 (`actionQueue.pending`/`runRemainingActions()` in `next/dist/client/components/app-router-instance.js`) — they're sent and awaited one at a time, not fire-and-forget in parallel; the next queued action only starts once the previous one's promise settles.

**This means a Server-Action-based health check alone is NOT sufficient — the retry submission itself must also stop being a Server Action, or it queues behind the exact hung original call it's meant to replace.** An earlier draft of this spec moved only the health check to a Route Handler and kept `scanQrAttemptConfirm` as a Server Action for both the original submission and every retry; review correctly caught that this doesn't fix anything — after a client-side timeout abandons the *promise* for a hung submission, the underlying action stays `pending` in Next's queue, and a subsequent `RETRY_ATTEMPT` (still a Server Action) sits behind it until the browser itself gives up on the original request, which can take minutes. The timeout only stops the UI from waiting; it does nothing to free the actual request queue.

**Decision: BOTH the health check and the scan submission become Route Handlers** (`src/app/api/scanner-health/route.ts` GET, `src/app/api/scan-qr-attempt/route.ts` POST), fetched directly with the browser's `fetch()`, each with its own `AbortController`-driven timeout. Route Handlers are not subject to the same-client action-queue serialization Server Actions have — a submission `fetch()` and a concurrent health-check `fetch()` (or a second submission `fetch()` for a retry) can all be in flight independently, each resolving or timing out on its own. `scanQrAttemptConfirmForCaller`'s existing logic moves into the Route Handler's POST body unchanged; the exported Server Action function (`scanQrAttemptConfirm`) is removed as a Server Action and replaced by the client calling the Route Handler directly.

### Retryable vs. non-retryable errors — the scan Route Handler returns a tagged-union JSON body; the real work is classifying the fetch() that hits it

Today `scanQrAttemptConfirm` always throws on any failure, and the client treats every throw identically. Moving this logic into a Route Handler changes WHERE classification happens but does not, by itself, fix the deeper problem review caught twice: **the errors that actually need distinguishing mostly happen BEFORE any server response exists to classify** — a dropped Wi-Fi connection makes the `fetch()` call itself reject on the client, never producing any JSON body at all, and several of today's pre-RPC checks (`verifyScannerScope`, the auth helper) themselves conflate "the thing I checked said no" with "I couldn't check, because the thing I'd ask was unreachable."

**The Route Handler's JSON response body** (only reached if the HTTP request itself completed):

```typescript
type ScanQrOutcome =
  | { ok: true; result: ScanQrResult }
  | { ok: false; retryable: true; reason: 'lock-contention' | 'upstream-unreachable' }
  | { ok: false; retryable: false; message: string };
```

**Classification happens at THREE layers, not one — this is the fix for review's B2/B3/B6 findings**:

1. **The `fetch()` call itself rejects or the response has no body** (network drop before any response, DNS failure, connection reset, the request aborted by the client's own timeout): the CLIENT classifies this directly as retryable, without needing the server to say anything — a rejected `fetch()` promise or a non-2xx response with no parseable JSON body is unambiguously a transport failure. This is the most common real failure mode on flaky venue Wi-Fi, and it was previously unhandled: an earlier draft only described classifying a server-returned `{ok:false}` body, never a `fetch()` that fails to produce a response at all.
2. **Inside the Route Handler, before calling `scan_qr_attempt_transactional`**: `verifyScannerScope` and the scanner-auth check (`requireScannerDeviceCaller`'s equivalent logic, now inlined in the handler) must each distinguish "the query completed and found no matching scope/session" (a real, deterministic denial) from "the query itself failed" (Supabase/Postgres unreachable from the Next server — a transport-shaped failure that happens to occur inside a pre-RPC check, not the RPC itself). Concretely: `verifyScannerScope`'s two queries today silently treat a populated `error` the same as a legitimately-empty result (`if (!session) throw ...`, `if (!count) throw ...`, neither checks whether `error` was actually populated). **Fix: both queries must check their own `error` first.** If either query itself failed (its `error` is populated), return `{ ok: false, retryable: true, reason: 'upstream-unreachable' }` immediately — never translate a failed existence-check into a confident "not found"/"not authorized" denial. Only an actually-empty, error-free result is a real, non-retryable denial.
3. **The RPC's own `{ data, error }`** (the call reached the database and got a real response): the table review's B6 finding requires an explicit mapping, not a loose "empty code means retryable" heuristic — error codes genuinely vary across failure shapes (a raw fetch rejection inside postgrest-js reports `code: ''`; a non-JSON 5xx gateway response reports `code: undefined`; PostgREST's own upstream-unreachable responses use `PGRST000`–`PGRST003`; Postgres-level transient conditions use `57014`/`40001`/`40P01`/`53300`/any `08*` class). Explicit table:
   - **Retryable** (`reason: 'upstream-unreachable'`): `error.code` is `''`, `undefined`, any of `PGRST000`–`PGRST003`, `57014`, `40001`, `40P01`, `53300`, or starts with `08`.
   - **Retryable** (`reason: 'lock-contention'`): `error.code === 'P0001'` AND `error.message` starts with the fixed, grep-able prefix `'LOCK_CONTENTION: '` — this migration gives the advisory-lock-exhausted `raise exception` this exact prefix specifically so the Route Handler can match on it reliably (matching on `code` alone can't distinguish this one `P0001` case from every other `raise exception` in the function, since every plain `raise exception` in PL/pgSQL defaults to `P0001`).
   - **Non-retryable**: `error.code === 'P0001'` without the lock-contention prefix (the idempotency-mismatch error, any other deterministic `raise exception`) → `{ ok: false, retryable: false, message: error.message }`.
   - Anything genuinely unclassifiable (a code not in any of the above buckets) defaults to **non-retryable** — review correctly flagged that defaulting an unknown shape to "retry forever" risks masking a real bug as transient noise; defaulting to "stop and show the operator something" is the safer failure mode for a code path this spec doesn't have a specific, verified reason to trust.

**Existing-test impact**: `tests/attendance/scan-qr-attempt-server-boundary.test.ts`'s `.rejects.toThrow(/Not authorized/)` assertions must become assertions against the Route Handler's returned status/JSON body instead of a thrown exception, and `scanner-client.tsx`'s existing `.then(result => dispatch(...))` call site is replaced entirely by a `fetch()`-based call (see Client Retry Loop below) — both are explicit tasks in this sub-project's own breakdown, not incidental fallout to discover later.

### New scanner state: `retrying`

`scan-state-machine.ts` gains a new state variant and transitions, following its existing pure-reducer, zero-dependency convention (testable the same way `scan-state-machine.test.ts` already does). **The idempotency key and any timestamp must be generated OUTSIDE the reducer and passed in as action payloads** — `crypto.randomUUID()` and `Date.now()` inside the reducer body would make it impure, breaking the file's own stated design goal and its existing `toEqual`-based tests, which assert on exact, predictable state shapes:

```typescript
ScanState:
  | { kind: 'ready' }
  | { kind: 'detected'; qrPayload: string }
  | { kind: 'submitting'; qrPayload: string; idempotencyKey: string; attemptSeq: number; startedAt: number }
  | { kind: 'retrying'; qrPayload: string; idempotencyKey: string; attemptSeq: number; startedAt: number }
  | { kind: 'result'; result: ScanQrResultLike }

ScanAction additions:
  | { type: 'SUBMIT_START'; idempotencyKey: string; attemptSeq: number; startedAt: number }  // caller generates key/seq/timestamp; existing SUBMIT_START gains these fields
  | { type: 'SUBMIT_TRANSPORT_FAILURE' }                          // from 'submitting' -> 'retrying'; startedAt/idempotencyKey/attemptSeq carry over unchanged from the prior state
  | { type: 'SUBMIT_REJECTED'; message: string }                  // from 'submitting' -> 'ready', non-retryable
  | { type: 'RETRY_ATTEMPT'; attemptSeq: number }                 // 'retrying' -> 'submitting'; same idempotencyKey/qrPayload/startedAt carried over, caller supplies a freshly-incremented attemptSeq
  | { type: 'CANCEL_RETRY' }                                      // 'retrying' -> 'ready', discards the key
```

**`attemptSeq`, not just `idempotencyKey`, is required for the stale-response guard** — review's B4 finding: retries intentionally reuse the same `idempotencyKey` across the whole retry cycle (that's the point — it's what makes the server-side operation idempotent), so a guard keyed only on the key cannot tell "this is a late response for a retry already superseded by yet another retry" from "this is the live, current attempt" — both share the same key. A monotonically-incrementing `attemptSeq`, generated by the caller (not the reducer) and incremented on every `SUBMIT_START`/`RETRY_ATTEMPT`, lets the stale-response guard (below) reject a late response from attempt N once attempt N+1 has started, even though both carry the identical `idempotencyKey`.

**`startedAt` is set once per retry *cycle*, not reset on every `submitting` entry** — review's B4 finding: the 30-second "Try Now/Cancel" message is meant to track how long the overall retry cycle (the thing a human is standing at a door waiting on) has been going, not how long the single most-recent attempt has taken. `startedAt` is set once on the transition into `retrying` from the ORIGINAL `submitting` (first `SUBMIT_TRANSPORT_FAILURE`) and then carried through unchanged across every subsequent `retrying → submitting → retrying` cycle — never reset by `RETRY_ATTEMPT`. This requires `submitting` to also carry `startedAt` (as shown in the type above) purely so it survives the round-trip back into `retrying` without needing a separate ref.

`SUBMIT_REJECTED`'s `message` must be surfaced somewhere the `ready` state can render it, since `ready` itself carries no data — add a sibling `lastRejection: string | null` piece of state alongside (not inside) the reducer's own state, cleared on the next `DETECT`, rather than overloading `ready`'s shape.

**What actually triggers the retry call after `RETRY_ATTEMPT`**: the existing submit-effect in `scanner-client.tsx` only fires when `state.kind === 'detected'` (the transition into `submitting` happens inside that effect, which then calls the scan Route Handler). `RETRY_ATTEMPT` moving `retrying → submitting` does NOT, by itself, invoke anything — a second effect, watching for entry into `submitting` from a retry (distinguishable by `idempotencyKey` already being set on the prior `retrying` state, vs. freshly generated for a brand-new `detected → submitting` transition), must explicitly `fetch()` the scan Route Handler again with the carried-over `qrPayload`/`idempotencyKey`. This is new wiring the reducer transition alone does not provide, and must be named explicitly in the implementation plan rather than left implicit.

**Existing call sites needing the new required fields — both named explicitly, not left for an implementer to discover**:
- `scanner-client.tsx`'s real submit effect (today's line ~144): generate `idempotencyKey` via `crypto.randomUUID()`, `attemptSeq` starting at `0`, and `startedAt` via `Date.now()` immediately before dispatching `SUBMIT_START`, and use the same `idempotencyKey` value in the Route Handler `fetch()` call that follows.
- The existing definite-offline short-circuit (today's line ~135, which immediately dispatches `SUBMIT_START` then `SUBMIT_ERROR` without ever attempting a network call): since `SUBMIT_START` now requires `idempotencyKey`/`attemptSeq`/`startedAt`, this site must still generate a throwaway `idempotencyKey` (even though it's never used for anything since the call never happens) purely to satisfy the action's shape — or, more simply, this path should bypass `SUBMIT_START`/`SUBMIT_ERROR` entirely and dispatch a new dedicated `OFFLINE_BLOCKED` action straight from `ready`/`detected` to `ready`, since conceptually it was never a submission attempt at all. Decide and record this explicitly during implementation rather than forcing a meaningless UUID through the "real" submission path.
- `crypto.randomUUID()` requires a secure context (HTTPS or `localhost`) — this is already implicitly required by this app's existing use of camera APIs (`getUserMedia`, also secure-context-only), so it introduces no new deployment constraint, but is worth confirming explicitly against however this project is tested on physical devices during implementation (a local network IP like `http://192.168.x.x` is NOT a secure context; use a tunneled HTTPS URL or test via `localhost` port-forwarding for on-device testing).
- `scan-state-machine.test.ts`'s existing bare `{ type: 'SUBMIT_START' }` dispatches (several call sites, asserting exact `toEqual` shapes) must be updated to supply the new required fields — an explicit test-file change, not an incidental side effect.

- The existing single-flight guarantee (`DETECT` is a no-op unless `state.kind === 'ready'`) extends correctly and needs no new guard code: `retrying` and `submitting` are both non-`ready`, and the reducer's existing `default: return state` branch already makes any action against an unhandled state/action pair a no-op.
- **Going offline mid-`retrying`** (the existing `SUBMIT_ERROR`/`'offline-blocked'` short-circuit at detect-time) continues to apply only at the `ready`→`detected`→`submitting` entry point, unchanged — a scan that's already in `retrying` simply continues its existing poll loop regardless of what `navigator.onLine` reports, since the health check (not `navigator.onLine`) is this design's actual source of truth for connectivity.
- **Stale-response guard**: a ref (not reducer state) holding both the currently-active `idempotencyKey` AND the currently-active `attemptSeq` lets a scan-submission `fetch()`'s resolved/rejected callback — which closes over whatever values existed when the call was made, not the state at the time it resolves — check that its own `attemptSeq` still matches the ref's current value before dispatching anything. `CANCEL_RETRY`, a fresh scan, or a newer `RETRY_ATTEMPT` all update the ref; a late response for a superseded `attemptSeq` is silently discarded, even though it may share the same `idempotencyKey` as the current attempt.
- **A late but valid success arriving while already back in `retrying`** (the original attempt finally resolves successfully, but only after the client had already given up and moved into a NEW retry cycle) is intentionally still discarded by the `attemptSeq` guard above, same as any other stale response — the subsequent `RETRY_ATTEMPT` will reach the server with the same idempotency key regardless and get the correct (already-committed) result on its own next attempt, so no data is lost, only a redundant round-trip.
- **Resuming the camera after Cancel**: the camera was stopped (`stop()`) when the original submission began. `CANCEL_RETRY`'s click handler must call `start()` synchronously within that same user-gesture handler — iOS Safari only permits media playback resumption inside a direct user-gesture callback, not inside a later `.then()` or state-effect callback, so this cannot be deferred into a `useEffect` reacting to the state change.

### Client retry loop (lives in `scanner-client.tsx`, alongside the existing submit-handling effect)

- On `SUBMIT_TRANSPORT_FAILURE` (dispatched when `scanQrAttemptConfirm` returns `{ ok: false, retryable: true }`, for either `reason`): enter `retrying`, start the health-check poll at a 2s interval, doubling up to a 10s ceiling (2s, 4s, 8s, 10s, 10s, ...), hitting the Route Handler described above.
- Each poll tick's `fetch()` carries its own `AbortController` timeout (e.g. 5s) so a hung health-check request doesn't itself stall the poll loop. On success: immediately dispatch `RETRY_ATTEMPT`, resetting the poll interval back to 2s for any *subsequent* failure of this same retry cycle.
- Listen for the browser's `online` event while in `retrying`: on fire, immediately run one health-check attempt out-of-cycle (don't wait for the next poll tick).
- A visible "Try Now" button, active throughout `retrying`, triggers the same immediate health-check-then-retry path.
- **Every scan submission — original AND retry — is now a `fetch()` to the scan Route Handler, never a Server Action call**, per the platform-constraint decision above. The client-side classification layer (layer 1 of the three-layer scheme above) lives at this `fetch()` call site: a rejected promise, an aborted request (via the submission's own `AbortController` timeout, e.g. 8s), or a non-2xx response with an unparseable body are all treated identically as `SUBMIT_TRANSPORT_FAILURE`; a 2xx response is parsed as the `ScanQrOutcome` JSON body and dispatched according to its `ok`/`retryable` fields.
- On `SUBMIT_TRANSPORT_FAILURE` (dispatched for any of: `fetch()` rejection, timeout-triggered `AbortController` abort, or a parsed `{ ok: false, retryable: true }` body): enter `retrying`.
- On `SUBMIT_REJECTED` (dispatched only for a parsed `{ ok: false, retryable: false }` body — this can only happen if a response was actually received, since a transport-shaped failure never reaches this branch): go straight to `ready` with the message surfaced via `lastRejection`, never entering `retrying` at all.
- At 30 continuous seconds in `retrying` (tracked via `startedAt`, which — per the state-machine section above — reflects the whole retry cycle's start, not the latest individual attempt): show a persistent message with "Try Now" and "Cancel" buttons. The background poll loop is NOT paused or altered by showing this message — it is purely informational, continuing to retry silently was the original problem being fixed, not something to preserve.
- "Cancel" dispatches `CANCEL_RETRY`, stopping the poll loop (clear the interval/timeout refs), resuming the camera synchronously (see above), and updating the stale-response-guard ref so any still-in-flight `fetch()` for the cancelled attempt is ignored when it eventually resolves. A subsequent scan of the same ticket is a new scan event with a new key; if the original attempt had actually succeeded before the cancel, the new attempt correctly surfaces the server's own `'duplicate'` result (already-existing, already-correct UX — `"Already Checked In"` / `"This participant has already been admitted to this session"`, no new message needed for this specific case).

### Health-check mechanism

A second Route Handler (`src/app/api/scanner-health/route.ts`, GET), reached through the same auth boundary and service-role client as the scan Route Handler above, performing one trivial real round-trip against the database — e.g. `service.from('scan_attempts').select('id', { head: true }).limit(0)` (head request, no row data transferred) — deliberately exercising the same authenticated path a real scan would use, not a generic "is the server reachable" ping that could return healthy while the database itself is unreachable or the caller's session has expired.

**Response codes, distinguishing "stop and re-authenticate" from "still unreachable, keep polling" — this distinction is the fix for review's Q3/B3 finding, which caught an earlier draft collapsing both into a single `401`:**
- **200**: the auth check succeeded AND the database round-trip succeeded. Dispatch `RETRY_ATTEMPT`.
- **401**: the auth check itself completed and genuinely rejected the caller (the scanner's session is truly invalid/expired — a real, deterministic "you are not who you claim to be," not a failed attempt to check). Treated as non-retryable: break out of the retry loop, surface a "re-authenticate" message, matching `SUBMIT_REJECTED`'s handling.
- **503**: either the auth check itself could not complete (its own underlying query failed with a transport-shaped error, not a clean "not found"/"not authorized" result) or the database round-trip failed. Treated as retryable: keep polling. This is the case an earlier draft of this spec incorrectly folded into `401` — a Supabase/Auth outage must not be reported as "this scanner needs to re-authenticate," since re-authenticating does nothing to fix an unreachable backend and would send the operator down the wrong troubleshooting path entirely.
- A `fetch()` that itself rejects (DNS failure, connection refused, before any HTTP response exists) is handled identically to a 503 — "still offline/unreachable," keep polling.

### Request/response shapes, named explicitly so an implementer isn't left to invent them

- **POST `/api/scan-qr-attempt`** — body `{ qrPayload: string, sessionId: string, deviceIdentifier: string | null, idempotencyKey: string }`; response body is the `ScanQrOutcome` JSON shown above, with HTTP status `200` for `ok: true` or any `ok: false` outcome the client is expected to parse normally (the distinction between retryable/non-retryable lives in the JSON body, not the HTTP status, since both are "the request completed successfully as far as HTTP is concerned" — only a non-2xx status or no body at all signals a transport-layer problem the client classifies itself without needing JSON).
- **GET `/api/scanner-health`** — no body; status code alone carries the result, per the 200/401/503 scheme above.

## Architecture — Client Side (Walk-In Admin Page)

The walk-in form (`walk-in-admission-form.tsx`) has no network-status awareness today and needs its own, simpler retry treatment — it is not part of the scanner's state machine or component tree, and its failure path is structurally different from the scanner's.

- **Same platform constraint as the scanner applies here too — `admitWalkIn` as a Server Action must be replaced the same way `scanQrAttemptConfirm` was.** A retry submission queued behind a hung original Server Action call has the identical problem on this page as on the scanner; there is nothing walk-in-specific that exempts it. `admitWalkIn`'s logic moves into a new Route Handler (`POST /api/admit-walk-in`), and the form calls it directly via `fetch()`, same three-layer classification scheme as the scanner (client-side `fetch()` rejection/timeout/no-body is layer 1, the pre-RPC identifier lookup and `requireAdmissionStaffCaller` equivalent is layer 2, the RPC's own `{ data, error }` is layer 3). The server-only identifier-resolution logic currently in `actions.ts` moves into this handler unchanged in substance.
- The Route Handler's JSON response is `{ ok: true, bookingId: string } | { ok: false, retryable: boolean, message: string }` — the walk-in equivalent of `ScanQrOutcome`, using the exact same three-layer classification rules (layer 2's identifier-lookup query must check its own `error` before concluding "no match found," same fix as `verifyScannerScope`'s).
- `idempotencyKey` is generated via `crypto.randomUUID()` once per form submission attempt (on the initial submit, not per retry), sent in the POST body, and threaded into the `admit_walk_in` RPC call as its new third parameter.
- The form's retry loop mirrors the scanner's: a client-side submission timeout (`AbortController`, same ~8s figure), a health-check poll (same 2s→10s backoff, same `online`-event and "Try Now" immediate-retry triggers), and a 30-second "Try Now"/"Cancel" message — all driven from the form's local state (a `retrying: boolean` plus `startedAt`/`idempotencyKey` kept in refs, not a full reducer; this page has no camera/single-flight concerns the scanner's reducer exists to solve). Disable the session-select and identifier-input fields while retrying — the identifier lookup is re-run on every retry via the same request, and allowing the operator to change the inputs mid-retry would silently detach the retry from what's actually displayed.
- A separate health-check Route Handler (`GET /api/admission-staff-health`), scoped to this page's actual auth boundary (`requireAdmissionStaffCaller`'s equivalent inline check, not `requireScannerDeviceCaller` — it cannot share the scanner's health check, which is gated on a different caller type entirely), using the same 200/401/503 scheme as the scanner's health check.
- **Note**: the idempotency key check in `admit_walk_in` runs after the session-status check (`'Session is not open for admission'`), so a retry attempted after the session's own status changed between the original attempt and the retry correctly surfaces that status error rather than the cached success — an accepted, narrow edge case (a session closing mid-retry-window), not a bug this design needs to additionally guard against.

## Non-Goals

- No offline queue, no local admission decisions, no "pending" status shown to operators, on either the scanner or the walk-in page.
- No change to the SQL function `admit_walk_in`'s return shape (still `uuid`/`booking_id`) beyond adding the new optional parameter — this is distinct from the TypeScript layer around it, which DOES change substantially (the Server Action becomes a Route Handler returning a tagged union, per the Walk-In Admin Page section above).
- No change to the PWA shell (`manifest.ts`, `sw.js`, `install-guidance.tsx`).
- No idempotency protection added to `src/lib/attendance/admission-management.ts`'s override-admission path or to `scan-attempt.ts`'s direct (non-QR) scan path — both continue calling `scan_attempt_transactional` with the new parameters defaulted to `null`, fully unaffected by this sub-project.
- No retry/idempotency design for any RPC beyond `scan_attempt_transactional` (and its `scan_qr_attempt_transactional` wrapper) and `admit_walk_in`.

## Testing Requirements

1. A QR scan retried with the same idempotency key after the original committed (simulating a lost response) returns the exact same row (same `id`, same `result`) without a second `attendance_records` insert or a second `scan_attempts` insert — covering both an `admitted` first attempt and a `duplicate`/`full`/`invalid_qr` first attempt.
2. A walk-in admission retried with the same idempotency key after the original committed returns the same `booking_id` without a second `session_bookings` row and without raising `'already has a booking'`.
3. The malformed-payload branch (`token_hash` null) retried with the same idempotency key returns the same row, not an incorrect mismatch error (`is not distinct from` NULL-safety check).
4. The same idempotency key presented with a different `token_hash`+`session_id` (QR) or a different `application_id`+`session_id` (walk-in) raises the distinct mismatch error, never returning stale data for a different request.
5. **Walk-in concurrency (backstop coverage, not the primary C1 regression test — that's test 2, run sequentially)**: two genuinely parallel `admit_walk_in` calls (e.g. `Promise.all` over two RPC calls with no client-side serialization, following the existing concurrency-test precedent in `tests/attendance/scan-attempt-concurrency-live.test.ts` and `tests/agenda/work-group-waitlist-live.test.ts`) with the same idempotency key both resolve to the same `booking_id`, with no `'already has a booking'` false rejection on either side. Note for whoever implements this: `Promise.all` alone doesn't force true overlap at the database level, so this test's value is as defense-in-depth coverage alongside test 2's sequential case, not as the sole proof the race is closed.
6. **QR idempotent replay changes the outcome correctly, concretely**: seed a session and one application such that WITHOUT idempotency a naive second call of the same scan would compute `'duplicate'` (since the first call's own admission is now visible to it), but WITH idempotency the second call instead replays the first call's actual original result (`'admitted'`/`'flexible_admitted'`) with the identical `scan_attempts.id` — assert exactly one `attendance_records` row and one `scan_attempts` row exist afterward, proving the idempotency check (not just luck) produced the replay rather than a coincidentally-identical independent computation.
7. A non-staff caller presenting a previously-used, valid idempotency key to `admit_walk_in` still gets `'Not authorized'` (idempotency check never bypasses the `is_staff()` gate) — AND, separately, an anon-key caller (no signed-in user at all, `auth.uid()` null) also gets rejected rather than silently succeeding, covering the `coalesce(is_staff(), false)` fix directly (the bare `if not is_staff()` form would let this specific anon case through, since `is_staff()` returns `NULL` rather than `false` for a profile-less caller).
8. A scanner whose assignment was revoked between its original (committed) attempt and a retry with the same key gets `'Not authorized for this session/room'` on the retry, not the original cached success. Note: in practice this specific case is caught client-side first by the scope-verification pre-check inside the scan Route Handler, so a test exercising the in-RPC ordering itself must call `scan_qr_attempt_transactional` directly (bypassing the Route Handler's own pre-check) to actually exercise the TOCTOU window this check protects.
9. The malformed-payload branch's `scan_fingerprint` computation does not raise `SQLSTATE 42883` (confirms the `extensions.digest(...)` schema-qualification fix; this would have been silently broken by the original unqualified-`digest()` draft).
10. The scan Route Handler returns `{ ok: false, retryable: true, reason: 'lock-contention' }` for the advisory-lock-exhausted case (matching on the fixed `'LOCK_CONTENTION: '` message prefix, not just `error.code`, since every `raise exception` shares `P0001`), and `{ ok: false, retryable: false }` for a genuine scope-revocation or the idempotency-mismatch error — covering the classification rules directly, not just their downstream client effects.
11. The scan Route Handler returns `{ ok: false, retryable: true, reason: 'upstream-unreachable' }` when the pre-RPC scope-verification query itself fails (simulate by having that query's own call throw/error, not by it returning a clean empty result) — distinguishing "I couldn't check" from "I checked and the answer was no," per the layer-2 classification fix.
12. **Backstop branch coverage**: force the `unique_violation` backstop to actually fire (not just the primary pre-lock check) in a scenario where it should raise the cross-key-reuse mismatch error (same idempotency key, deliberately different session/application, racing before either's lock serializes them) — confirms the three-way `constraint_name` branching returns an error, not another request's row, for this case. This is deliberately a harder test to construct reliably and may need direct, carefully-sequenced SQL manipulation (e.g. two sessions within the same transaction scope, or mocking the constraint check) rather than a simple `Promise.all` — note this explicitly as an implementation challenge rather than skipping the case silently.
13. Existing callers (`scan-attempt.ts`'s direct path, `admission-management.ts`'s override path) continue to work unchanged with no idempotency key passed (`null` defaults, zero behavior change) — a straightforward regression check, not new behavior.
14. Client (component-level, not live DB): a non-retryable server rejection (e.g. the new mismatch error, or a scope-revoked rejection) does not enter the `retrying` loop — it goes straight to a terminal error message, matching the state machine's `SUBMIT_REJECTED` transition.
15. Client (component-level): a `fetch()` rejection (simulated network failure, not a parsed JSON body) is classified identically to a parsed `{ ok: false, retryable: true }` body — both must enter `retrying`, covering layer-1 classification directly (this was the previously-unhandled "most common real failure mode" review flagged).
16. Client (component-level): a late-arriving response for a superseded attempt (a stale `attemptSeq`, even when the `idempotencyKey` is identical to the current attempt) is discarded, never rendered — distinct from testing only a mismatched key, since retries intentionally reuse the same key.
17. Client (component-level): `startedAt` is preserved across a `retrying → submitting → retrying` cycle (a second `SUBMIT_TRANSPORT_FAILURE` does not reset the 30-second countdown) — covering the fix for the "the timeout message never appears if submits keep failing after a successful health check" gap.
18. Client (component-level): `CANCEL_RETRY` followed by a fresh `DETECT`/`SUBMIT_START` on the same QR payload generates a new idempotency key (not a reuse of the cancelled one).
19. Client (component-level): the single-flight guarantee extends correctly to the new `retrying` state — a `DETECT` action while in `retrying` is a no-op, same as while `submitting`.
20. Walk-in form: a retried submission after a transport failure reuses the same idempotency key across all retries of that one submission, and the session/identifier inputs are disabled while retrying.
21. The health-check Route Handler returns `503` (not `401`) when the auth check's own underlying query fails (simulated upstream outage), and the client keeps polling rather than treating it as a terminal re-authentication state — covering the fix for the earlier draft's 401/503 conflation.
