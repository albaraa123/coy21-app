# Offline Scanning Support (5b) — Design Spec

Sub-project 5b of the 6-part COY21 platform decomposition. Depends on nothing merged after 5a (live operations dashboard, merged to `master`). Deferred from 5a's scope explicitly — see `docs/superpowers/specs/2026-10-05-ops-dashboard-design.md`'s Out of Scope section.

## Problem

The scanner app (`src/components/scanner/scanner-client.tsx`) is currently strictly online-only: `use-network-status.ts` wraps `navigator.onLine` and the browser's `online`/`offline` events, and the client short-circuits every submit attempt while offline — it never even calls the server. A failed network call is bucketed into a three-way taxonomy (`offline-blocked`, `uncertain`, `server`) purely for operator-facing messaging; there is no retry, no queue, no persistence of any kind.

The walk-in admission page (`src/app/[locale]/(admin)/attendance/walk-in/`) has no network-status awareness at all today — no offline detection, no retry, nothing. It's a separate admin page (staff-only, `requireAdmissionStaffCaller`), not part of the scanner flow, and is addressed as its own track below rather than conflated with the scanner.

One prior spec (`2026-07-31-flexible-admission-qr-attendance-design.md`, lines 17, 298, 347) flagged offline behavior as a known, explicitly deferred gap, anticipating a future "PWA offline-queue/sync" follow-up spec, and established one hard constraint any such design must preserve: **no local "optimistic" admission that could double-book on reconnect.** That source does not itself forbid a queue — it only forbids a queue (or any design) making a local admission decision the server hasn't confirmed. This spec's choice to build auto-retry instead of a queue is **this spec's own scope decision**, made because a queue gains nothing here (see Scope Decision below), not something the earlier spec mandates.

**The actual failure modes, verified against current code, are asymmetric between the two admission paths:**

- **QR path**: a naive retry after a lost response already resolves safely today. `scan_attempt_transactional` is idempotent in effect — a retried scan of an already-admitted ticket returns `result: 'duplicate'`, which `result-presentation.ts` renders as `severity: 'attention'` ("informational, not an error — they're already in"), not a rejection. Idempotency keys for this path are a UX/efficiency improvement (skip re-running the full decision tree, restore the original `admitted`/`flexible_admitted` result and participant summary instead of a generic `duplicate`), not a correctness fix for a false rejection.
- **Walk-in path**: a naive retry after a lost success genuinely produces a false rejection today. `admit_walk_in`'s pre-insert check (`'This participant already has a booking for this session'`) fires before reaching any uniqueness constraint, so a retried walk-in of an already-admitted participant raises a hard error with no idempotent fallback. **This is the one genuine correctness bug this spec exists to fix**, and the walk-in design below must close it precisely.

## Scope Decision

**Build:** client-side auto-retry for both the scanner and the walk-in admin page, each on top of its own existing architecture, protected by server-side idempotency keys so a lost response can never produce a wrong outcome (double-admission, or — walk-in specifically — a false rejection of an already-admitted participant).

**Do not build:** any offline queue, any local admission decision, any "pending sync" state visible to the operator, any change to the PWA shell (`manifest.ts`, `sw.js`, `install-guidance.tsx` stay untouched — those remain scoped to static-asset caching/installability per their own existing comments).

## Architecture — Server Side

### Two independent idempotency mechanisms, on the tables each function actually writes to

- **QR scan path**: `scan_attempt_transactional` (the function that actually performs every insert — `scan_qr_attempt_transactional` is a thin bridge that delegates to it, see Signature Changes below) inserts exactly one `scan_attempts` row per call in the common case, but has two exception paths that insert nothing at all (advisory-lock-exhausted at line 142-144 of `20261006050000_walk_in_admission.sql`, and scanner-scope-revoked at line 160-162) — both `raise exception`, propagating as a thrown error. Gets `scan_attempts.idempotency_key` (`uuid`, nullable, unique index) plus `scan_attempts.scan_fingerprint` (`bytea`, nullable — a derived fingerprint, not the raw credential hash; see Column Content below).
- **Walk-in path**: `admit_walk_in` writes to `session_bookings` and `attendance_records`, returns only a `booking_id` (`uuid`). Gets `session_bookings.idempotency_key` (`uuid`, nullable, unique index).

Both keys are nullable so existing rows and existing callers (the override path in `src/lib/attendance/admission-management.ts`, and `src/lib/attendance/scan-attempt.ts`'s non-QR scan path) are completely unaffected — every new parameter defaults to `null`, and a `null` key means "skip the idempotency check entirely, behave exactly as today." Postgres's unique index semantics (distinct `NULL`s never conflict) mean this requires no backfill and no behavior change for any caller that doesn't pass a key.

### Idempotency check placement — AFTER auth, AFTER the serialization point, not "at the very top"

This is the one point both admission functions must get right, and it differs by function because their serialization mechanisms differ:

**`admit_walk_in`** (current body: `20261006052000_admit_walk_in_shared_advisory_lock.sql`):
1. `is_staff()` check (line 41) — unchanged, runs first. An idempotency lookup must never run before authorization; returning a cached `booking_id` to an unauthorized caller would be a privilege leak.
2. Application-accepted check (line 45) — unchanged.
3. `select ... for update` on `sessions` (line 49) — unchanged.
4. **New: idempotency key check goes here, immediately after the advisory lock (line 61) and before the capacity/duplicate-booking checks (line 71-89).** This is the fix for the race the naive design misses: if the key check only happened via a `unique_violation` catch around the final `session_bookings` insert (line 91-93), a concurrent retry with the same key would reach the pre-insert `'already has a booking'` check (line 77-82) first — once the original request has committed, that check fires and raises the exact false rejection this spec exists to prevent, never reaching the insert at all. Checking immediately after the lock means every retry with the same key sees the first request's committed row (under READ COMMITTED, once serialized by the lock) and returns it directly, never reaching the business checks that would misfire.
5. If a matching key exists: compare `application_id`+`session_id` against the stored row's. Match → return the stored `booking_id` immediately. Mismatch → raise `'Idempotency key reused with different admission data'`.
6. If no matching key: proceed with existing logic unchanged, write the key into the final `session_bookings` insert.
7. **Race backstop**: wrap the `session_bookings` insert in `begin...exception when unique_violation`, but — same caveat as the QR path below — `session_bookings_active_unique` (`20260823020000_session_bookings.sql`) is a second, unrelated constraint on this same table that can also legitimately raise `unique_violation` for a real conflict unrelated to key reuse. Use `get stacked diagnostics` to check `constraint_name`: re-fetch-and-return the cached `booking_id` only when the violated constraint is the new `idempotency_key` unique index; `raise;` unchanged for `session_bookings_active_unique`. The serialization point is actually the `select ... for update` on `sessions` (line 49, not the advisory lock at line 61 — a second same-key caller blocks there, not at the lock, since `for update` itself serializes against another in-progress transaction touching the same session row), so this backstop is pure defense in depth for an already-closed race, not the primary mechanism.

**`scan_attempt_transactional`** (current body: `20261006050000_walk_in_admission.sql` lines 101-266):
1. Advisory lock acquisition loop (lines 135-144) — unchanged. If lock acquisition fails after retries, this raises an exception with no insert at all; a client-side retry of the *whole attempt* (not just the idempotency wrapper) is the correct response, since nothing was recorded (see Client-Side Error Classification below — this is a retryable error).
2. Scanner-scope re-check (lines 152-163) — unchanged, runs with the lock held. If scope was revoked, this raises `'Not authorized for this session/room'` with no insert. **Decision: the idempotency check runs AFTER this scope re-check, not before.** Rationale: replaying a completed admission to a scanner whose assignment was just revoked mid-shift should still surface the auth failure on retry attempts after revocation, not silently hand back a stale success — the scope check protects a real-time security boundary, and an idempotent replay must not bypass it.
3. **New: idempotency key check goes here**, immediately after the scope re-check, before the application/session lookup (line 165) and before any part of the admission-decision tree.
4. If a matching key exists: compare the stored row's `scan_fingerprint` against the incoming fingerprint using `is not distinct from` (not `=` — see Mismatch Check Details below, this handles the malformed/unresolved-credential branches where the fingerprint input is legitimately `null`-derived), AND compare `session_id`. Match on both → return the stored row immediately (no re-execution of the decision tree, no second `attendance_records` insert). Mismatch on either → raise `'Idempotency key reused with different scan data'`.
5. If no matching key: proceed with existing logic completely unchanged through the full decision tree (lines 165-258).
6. **The final insert at lines 260-262 is the only place the key is written.** The idempotency check in step 4 runs while the per-session advisory lock (acquired in step 1, held until the transaction ends) is still held, so a second caller with the same key — necessarily targeting the same session, since the check also compares `session_id` — cannot even begin executing until the first caller's transaction has fully committed and released the lock. By the time the second caller's key check runs, it is a fresh statement under READ COMMITTED and sees the first caller's committed row directly. The second caller never reaches the decision tree at all; there is no window for it to compute an independent decision or insert a second `attendance_records` row.
   - **`unique_violation` backstop, scoped correctly**: wrap the final insert in `begin...exception when unique_violation`, but do NOT treat every `unique_violation` as "the same key was reused — return the cached row." Two distinct unique constraints could fire here: `scan_attempts`'s own new `idempotency_key` unique index (the only case that means "re-fetch and return"), and `attendance_records_no_duplicate_active` (an unrelated constraint that can legitimately fire for a *different* reason and must propagate as its own error, not be swallowed). Use `get stacked diagnostics v_constraint = constraint_name;` inside the exception handler and branch on it explicitly — re-fetch-and-return only when `v_constraint` is the idempotency index's name; `raise;` (re-raise unchanged) for anything else. The lock makes this backstop fire only for the now-impossible-by-construction pre-lock race across *different* sessions reusing the same key (caught by the mismatch check in step 4, not this backstop) — it exists purely as defense in depth, not as a case this design actually expects to hit in practice.
7. **The two unresolved-credential early-return branches in `scan_qr_attempt_transactional`** (malformed hash, no active credential match — lines 291-306 of the file, which insert directly rather than delegating to `scan_attempt_transactional`) need their own, independent idempotency check and insert, since they never reach `scan_attempt_transactional`'s lock at all. They take no advisory lock today and don't need one added — each is a single, unconditional insert, so the insert-level `unique_violation` catch alone is sufficient there (no decision tree to protect from double-execution, since there is no decision — it's an unconditional `invalid_qr`), with the same constraint-name branching as step 6 above.

### Signature changes

- `scan_attempt_transactional(p_application_id, p_session_id, p_scanned_by, p_device_identifier, p_time_slot_group_key, p_is_override_caller default false, p_scanner_user_id default null, p_idempotency_key uuid default null, p_token_hash bytea default null)` — two new trailing optional parameters, both defaulting to `null`. `p_token_hash` is accepted here (not only in the wrapper) because the idempotency check and the final insert both need it, and both live in this function per the placement rules above.
- `scan_qr_attempt_transactional(..., p_idempotency_key uuid default null)` — one new trailing parameter, forwarded straight through to `scan_attempt_transactional` alongside the `p_token_hash` it already has from its own existing parameter list. Its own two unresolved-credential branches use `p_idempotency_key` directly for their own independent check (point 7 above).
- `admit_walk_in(p_application_id, p_session_id, p_idempotency_key uuid default null)` — one new trailing parameter.
- Every signature change needs: `drop function if exists` on the old arity (matching this codebase's established precedent in `20261006050000_walk_in_admission.sql` lines 98-99), the full `revoke`/`grant` restatement these functions already carry, and regenerating `src/types/database.ts` afterward.
- **Existing callers unaffected**: `src/lib/attendance/scan-attempt.ts`'s direct (non-QR) scan path, and `src/lib/attendance/admission-management.ts`'s override-admission path, both call `scan_attempt_transactional` without the new parameters today and must continue to compile/work unchanged — passing `null` for both new parameters is the default, so no call-site change is required there. This sub-project touches only `scan-qr-attempt.ts`'s call site and the walk-in action.

### Mismatch check details

- Use `is not distinct from` for the stored `scan_fingerprint` comparison, never `=` — the malformed-payload branch passes `p_token_hash = null` today (`scan-qr-attempt.ts`), which feeds into a fingerprint computed from a `null` input, and `null = null` evaluates to `null` (neither true nor false) in SQL — comparing two such fingerprints under plain `=` would incorrectly fail a legitimate retry of a malformed-payload scan. `is not distinct from` treats equal fingerprints (including two both derived from `null`) as equal, exactly as intended.
- The comparison must include `session_id` as well as the fingerprint/`application_id` — a client bug that reuses a key across two different sessions is exactly the kind of misuse this check exists to catch, which the fingerprint alone wouldn't detect (it's already derived including `session_id`, per the Column Content section below, but the check should compare `session_id` explicitly too for clarity rather than relying solely on the fingerprint's own construction).

### Column content — `scan_attempts.scan_fingerprint` is a derived fingerprint, not the raw credential hash

`scan_attempts` already has broader read access than `qr_credentials` (`scan_attempts_scanner_select`/staff policies grant read access to scanner-device and staff roles; `qr_credentials` access is far narrower). Storing the raw `token_hash` value on every `scan_attempts` row would copy credential-lookup material into a more widely readable table purely for an idempotency-mismatch check that doesn't need the real hash — it only needs *something* that changes if the QR changes. Store a derived fingerprint instead, under a column named `scan_fingerprint bytea` (not `token_hash` — that name would misleadingly imply the real credential hash is stored):

```sql
extensions.digest(coalesce(p_token_hash, ''::bytea) || uuid_send(p_session_id), 'sha256')
```

Two details this exact expression exists to get right, both found during spec review against the real schema:
- **Schema-qualify `digest()` as `extensions.digest(...)`, never bare `digest(...)`.** `scan_attempt_transactional` runs under a hardened `set search_path = public, pg_temp` (no `extensions`, where pgcrypto is installed on this Supabase project). This exact mistake already happened once in this codebase's history — `admit_walk_in` hit `SQLSTATE 42883: function digest(text, unknown) does not exist` for precisely this reason, fixed in `20261006051000_fix_admit_walk_in_search_path.sql`. Schema-qualifying the call avoids needing to widen this function's own search_path.
- **Concatenate as `bytea`, never mix in a bare `::text` cast.** `p_session_id::text` concatenated directly against a `bytea` with `||` has no implicit cast in either direction; Postgres resolves it via the generic `anynonarray || text` operator, producing a *text* value (the bytea's `\x`-prefixed printed representation, concatenated with the uuid string) rather than a byte sequence — which would make the fingerprint's actual value depend on the session's `bytea_output` setting, a dependency with no reason to exist here. `uuid_send(p_session_id)` returns the uuid's raw 16-byte form directly, keeping the whole expression `bytea` throughout with no cast-dependent behavior.

Computed the same way in both the malformed-payload/unresolved-credential branches and the resolved-credential branch. Because of the `coalesce`, this expression is never itself `null` — the `is not distinct from` comparison in Mismatch Check Details above is harmless to keep regardless, but the NULL-safety concern it was originally written to address doesn't actually arise once this `coalesce` is in place.

## Architecture — Client Side (Scanner)

### Platform constraint: Next.js Server Actions dispatched from one client are processed one at a time

This governs the whole client design below and must be designed around, not discovered mid-implementation: Next.js serializes Server Actions dispatched from the same client — they're sent and awaited one at a time, not fire-and-forget in parallel. If the health check were itself a Server Action, it would queue behind a hung `scanQrAttemptConfirm` call and never actually run until that call's own timeout/abort frees the queue — silently defeating both the health-check poll and the "Try Now" button for exactly the hung-request scenario they exist to handle.

**Decision: the health check is a plain Route Handler (`src/app/api/scanner-health/route.ts`), fetched directly with the browser's `fetch()` plus an `AbortController`-driven timeout — not a Server Action.** Route Handlers aren't subject to the same-client serialization Server Actions have, so a health-check `fetch()` can run concurrently with (and resolve independently of) an in-flight, possibly-hung `scanQrAttemptConfirm` call. The actual retry submission (`RETRY_ATTEMPT`) remains a Server Action, same as the original submission — only the health check needs the Route Handler treatment, since it's the thing that must keep working while a submission might be stuck.

### Retryable vs. non-retryable errors — `scanQrAttemptConfirm` returns a tagged union, never throws for an expected failure

Today `scanQrAttemptConfirm` always throws on any failure (`verifyScannerScope`'s pre-call checks throw directly; the RPC's own `{ data, error }` is converted to a throw via `if (error) throw new Error(error.message)`), and the client treats every throw identically, bucketed only by `navigator.onLine` state at catch time. This is insufficient for auto-retry in two concrete ways found during spec review:
- A deterministic rejection (scope revoked — thrown by `verifyScannerScope` BEFORE the RPC is even called, session expired, the new idempotency-mismatch error) would retry forever today's way, because the health check only verifies `requireScannerDeviceCaller` succeeds, not that scope is still valid — so a revoked-scope scanner would see "server is healthy" and keep re-submitting a scan that's rejected every single time for a reason no retry can fix.
- Conversely, a genuine transport failure (Next's server-side fetch to Supabase itself fails) surfaces through supabase-js as a resolved `{ error: { message: 'TypeError: fetch failed', code: '' } }`, not a thrown exception — classifying "the RPC resolved with an error" as uniformly non-retryable would wrongly treat a database-unreachable condition (exactly the case retrying should eventually fix) as a hard stop.

**Change**: `scanQrAttemptConfirm` returns a tagged union instead of throwing for any failure mode this spec's retry logic needs to distinguish:

```typescript
type ScanQrOutcome =
  | { ok: true; result: ScanQrResult }
  | { ok: false; retryable: true; reason: 'transport' | 'lock-contention' }
  | { ok: false; retryable: false; message: string };
```

Classification rules, in order:
1. `verifyScannerScope`'s pre-call throws (`'Session not found'`, `'Not authorized for this session/room'`) are caught at the top of `scanQrAttemptConfirmForCaller` and returned as `{ ok: false, retryable: false, message }` — never retryable, since re-attempting the identical call changes nothing about the caller's revoked scope.
2. The RPC's own `{ data, error }`: if `error.code` is the specific lock-exhausted message (give it its own distinguishable `errcode`/message prefix in the migration, e.g. a fixed `'LOCK_CONTENTION: '` prefix on that one `raise exception`, rather than relying on substring-matching a long interpolated message) → `{ ok: false, retryable: true, reason: 'lock-contention' }`. Any other populated `error` with a real SQLSTATE from a `raise exception` (the idempotency-mismatch error, any future deterministic rejection) → `{ ok: false, retryable: false, message: error.message }`.
3. An `error` with an empty/network-shaped code (no real SQLSTATE — the "Supabase itself unreachable from the Next server" case) → `{ ok: false, retryable: true, reason: 'transport' }`. This is the opposite of a naive "any RPC error means stop retrying" rule, and is specifically what review caught: database-unreachable must stay retryable, not be misclassified alongside genuine business rejections.
4. Success → `{ ok: true, result }`.
5. A thrown exception that reaches neither of the above (an actual uncaught transport-layer exception from the `fetch()` underneath supabase-js, e.g. a connection reset) is caught at the outermost level of `scanQrAttemptConfirmForCaller` and also mapped to `{ ok: false, retryable: true, reason: 'transport' }`.

**Existing-test impact, to be addressed as part of implementation, not silently left broken**: `tests/attendance/scan-qr-attempt-server-boundary.test.ts`'s existing `.rejects.toThrow(/Not authorized/)` assertion and `scanner-client.tsx`'s existing `.then(result => dispatch({ type: 'SUBMIT_SUCCESS', result }))` both assume the current throw-always contract and must be updated to the new tagged-union return shape as part of this sub-project's own task breakdown — not treated as an unrelated, discoverable-later regression.

### New scanner state: `retrying`

`scan-state-machine.ts` gains a new state variant and transitions, following its existing pure-reducer, zero-dependency convention (testable the same way `scan-state-machine.test.ts` already does). **The idempotency key and any timestamp must be generated OUTSIDE the reducer and passed in as action payloads** — `crypto.randomUUID()` and `Date.now()` inside the reducer body would make it impure, breaking the file's own stated design goal and its existing `toEqual`-based tests, which assert on exact, predictable state shapes:

```typescript
ScanState:
  | { kind: 'ready' }
  | { kind: 'detected'; qrPayload: string }
  | { kind: 'submitting'; qrPayload: string; idempotencyKey: string }
  | { kind: 'retrying'; qrPayload: string; idempotencyKey: string; startedAt: number }
  | { kind: 'result'; result: ScanQrResultLike }

ScanAction additions:
  | { type: 'SUBMIT_START'; idempotencyKey: string }               // caller generates the key; existing SUBMIT_START gains this field
  | { type: 'SUBMIT_TRANSPORT_FAILURE'; startedAt: number }        // from 'submitting' -> 'retrying'; caller supplies Date.now()
  | { type: 'SUBMIT_REJECTED'; message: string }                  // from 'submitting' -> 'ready', non-retryable
  | { type: 'RETRY_ATTEMPT' }                                     // 'retrying' -> 'submitting', same idempotencyKey/qrPayload carried over
  | { type: 'CANCEL_RETRY' }                                      // 'retrying' -> 'ready', discards the key
```

`SUBMIT_REJECTED`'s `message` must be surfaced somewhere the `ready` state can render it, since `ready` itself carries no data — add a sibling `lastRejection: string | null` piece of state alongside (not inside) the reducer's own state, cleared on the next `DETECT`, rather than overloading `ready`'s shape.

**What actually triggers the retry call after `RETRY_ATTEMPT`**: the existing submit-effect in `scanner-client.tsx` only fires when `state.kind === 'detected'` (the transition into `submitting` happens inside that effect, which then calls `scanQrAttemptConfirm`). `RETRY_ATTEMPT` moving `retrying → submitting` does NOT, by itself, invoke anything — a second effect (or the same effect widened to also watch `state.kind === 'submitting'` entered via a retry, distinguished by presence of `idempotencyKey` already being set rather than freshly generated) must explicitly call `scanQrAttemptConfirm` again with the carried-over `qrPayload`/`idempotencyKey` whenever `retrying → submitting` fires. This is new wiring the reducer transition alone does not provide, and must be named explicitly in the implementation plan rather than left implicit.

- The existing single-flight guarantee (`DETECT` is a no-op unless `state.kind === 'ready'`) extends correctly and needs no new guard code: `retrying` and `submitting` are both non-`ready`, and the reducer's existing `default: return state` branch already makes any action against an unhandled state/action pair a no-op.
- **Going offline mid-`retrying`** (the existing `SUBMIT_ERROR`/`'offline-blocked'` short-circuit at detect-time, lines 135-142 of `scanner-client.tsx`) continues to apply only at the `ready`→`detected`→`submitting` entry point, unchanged — a scan that's already in `retrying` simply continues its existing poll loop regardless of what `navigator.onLine` reports, since the health check (not `navigator.onLine`) is this design's actual source of truth for connectivity.
- **Stale-response guard**: a ref (not reducer state) holding the currently-active `idempotencyKey` lets a `scanQrAttemptConfirm` promise's `.then()`/`.catch()` callback — which closes over whatever state existed when the call was made, not the state at the time it resolves — check that the key it started with still matches the ref's current value before dispatching anything. A `CANCEL_RETRY` or a fresh scan both update the ref; a late response for a superseded key is silently discarded.
- **Resuming the camera after Cancel**: the camera was stopped (`stop()`) when the original submission began. `CANCEL_RETRY`'s click handler must call `start()` synchronously within that same user-gesture handler — iOS Safari only permits media playback resumption inside a direct user-gesture callback, not inside a later `.then()` or state-effect callback, so this cannot be deferred into a `useEffect` reacting to the state change.

### Client retry loop (lives in `scanner-client.tsx`, alongside the existing submit-handling effect)

- On `SUBMIT_TRANSPORT_FAILURE` (dispatched when `scanQrAttemptConfirm` returns `{ ok: false, retryable: true }`, for either `reason`): enter `retrying`, start the health-check poll at a 2s interval, doubling up to a 10s ceiling (2s, 4s, 8s, 10s, 10s, ...), hitting the Route Handler described above.
- Each poll tick's `fetch()` carries its own `AbortController` timeout (e.g. 5s) so a hung health-check request doesn't itself stall the poll loop. On success: immediately dispatch `RETRY_ATTEMPT`, resetting the poll interval back to 2s for any *subsequent* failure of this same retry cycle.
- Listen for the browser's `online` event while in `retrying`: on fire, immediately run one health-check attempt out-of-cycle (don't wait for the next poll tick).
- A visible "Try Now" button, active throughout `retrying`, triggers the same immediate health-check-then-retry path.
- **Client-side submission timeout**: race every `scanQrAttemptConfirm` call against an `AbortController`-driven timer (e.g. 8s) — a hung request (connected but never responding, plausible on flaky venue Wi-Fi) must not leave the UI stuck in `submitting` indefinitely. A timeout dispatches `SUBMIT_TRANSPORT_FAILURE`, treated as retryable, not a rejection. Note this is a client-side abandonment of that specific call, not a cancellation of the underlying request on the server — the idempotency key ensures a late-arriving success for an abandoned call is still handled correctly if it arrives after a subsequent retry (the stale-response guard discards it; the server-side data is correct either way since the key makes the operation itself idempotent).
- On `SUBMIT_REJECTED` (returned when `scanQrAttemptConfirm` resolves `{ ok: false, retryable: false }`): go straight to `ready` with the message surfaced via `lastRejection`, never entering `retrying` at all.
- At 30 continuous seconds in `retrying` (tracked via `startedAt`): show a persistent message with "Try Now" and "Cancel" buttons. The background poll loop is NOT paused or altered by showing this message — it is purely informational, continuing to retry silently was the original problem being fixed, not something to preserve.
- "Cancel" dispatches `CANCEL_RETRY`, stopping the poll loop (clear the interval/timeout refs), resuming the camera synchronously (see above), and discarding the idempotency key via the stale-response-guard ref. A subsequent scan of the same ticket is a new scan event with a new key; if the original attempt had actually succeeded before the cancel, the new attempt correctly surfaces the server's own `'duplicate'` result (already-existing, already-correct UX — `"Already Checked In"` / `"This participant has already been admitted to this session"`, no new message needed for this specific case).

### Health-check mechanism

A new Route Handler (`src/app/api/scanner-health/route.ts`, GET), reached through the same `requireScannerDeviceCaller` trust boundary as `scanQrAttemptConfirm` (Route Handlers can call the same server-only auth helpers Server Actions do) and the same service-role client, performing one trivial real round-trip against the database — e.g. `service.from('scan_attempts').select('id', { head: true }).limit(0)` (head request, no row data transferred) — deliberately exercising the same authenticated path a real scan would use, not a generic "is the server reachable" ping that could return healthy while the database itself is unreachable or the caller's session has expired. Returns a plain `200`/`401`/`500` status the client's `fetch()` call checks directly, not a Server Action result.

- If the caller's scanner session has itself expired (`requireScannerDeviceCaller` fails inside the Route Handler), it returns `401` — the client treats this distinctly from a network-level `fetch()` rejection: a `401` means "stop polling, this scanner needs to be re-authenticated," surfaced the same way a `SUBMIT_REJECTED` would be (break out of the retry loop, show a clear message), not silently retried forever. A `fetch()` that itself throws (DNS failure, connection refused) means "still offline/unreachable," keep polling.

## Architecture — Client Side (Walk-In Admin Page)

The walk-in form (`walk-in-admission-form.tsx`) has no network-status awareness today and needs its own, simpler retry treatment — it is not part of the scanner's state machine or component tree, and its failure path is structurally different from the scanner's.

- **Failure routing is different from the scanner's, and the first draft of this spec had this backwards.** `admitWalkIn` returns `{ error: string | null, bookingId?: string }` for every *server-side* failure (bad identifier, RPC rejection) — but a genuine transport failure (the request to the server action itself fails to complete) throws into the form's own `try/catch` (`walk-in-admission-form.tsx`), same as `requireAdmissionStaffCaller`'s own auth failures. The retry trigger must be driven from that `catch` block, not from inspecting `result.error`'s string content — mirroring the scanner's tagged-union approach: `admitWalkIn` should itself return a tagged union analogous to `ScanQrOutcome` (`{ ok: true, bookingId } | { ok: false, retryable: boolean, message }`), with `requireAdmissionStaffCaller` failures and genuine transport failures both caught inside the action and classified the same way `scanQrAttemptConfirm` classifies them, rather than ever reaching the form's `catch` as an unclassified throw.
- `admitWalkIn` gains an `idempotencyKey` parameter, generated via `crypto.randomUUID()` once per form submission attempt (on the initial submit, not per retry), threaded into the `admit_walk_in` RPC call as its new third parameter.
- On a `retryable: true` result: show a "Connection lost — retrying…" state with the same "Try Now"/"Cancel" affordances as the scanner, reusing the same idempotency key across retries of this one submission. Disable the session-select and identifier-input fields while retrying — the identifier lookup is re-run on every retry via the same server action, and allowing the operator to change the inputs mid-retry would silently detach the retry from what's actually displayed.
- A separate health-check Route Handler, scoped to `requireAdmissionStaffCaller` instead of `requireScannerDeviceCaller` (this page's actual auth boundary — it cannot share the scanner's health check, which is gated on a different caller type entirely), following the exact same "real round-trip through the real auth boundary" principle as the scanner's.
- No camera, no single-flight state machine needed — the existing `submitting` boolean plus a new `retrying` boolean on the form's local state is sufficient; this does not need the scanner's full reducer treatment.
- **Note**: the idempotency key check in `admit_walk_in` runs after the session-status check (`'Session is not open for admission'`), so a retry attempted after the session's own status changed between the original attempt and the retry correctly surfaces that status error rather than the cached success — an accepted, narrow edge case (a session closing mid-retry-window), not a bug this design needs to additionally guard against.

## Non-Goals

- No offline queue, no local admission decisions, no "pending" status shown to operators, on either the scanner or the walk-in page.
- No change to `admit_walk_in`'s return shape (still `uuid`/`booking_id`) beyond adding the new optional parameter.
- No change to the PWA shell (`manifest.ts`, `sw.js`, `install-guidance.tsx`).
- No idempotency protection added to `src/lib/attendance/admission-management.ts`'s override-admission path or to `scan-attempt.ts`'s direct (non-QR) scan path — both continue calling `scan_attempt_transactional` with the new parameters defaulted to `null`, fully unaffected by this sub-project.
- No retry/idempotency design for any RPC beyond `scan_attempt_transactional` (and its `scan_qr_attempt_transactional` wrapper) and `admit_walk_in`.

## Testing Requirements

1. A QR scan retried with the same idempotency key after the original committed (simulating a lost response) returns the exact same row (same `id`, same `result`) without a second `attendance_records` insert or a second `scan_attempts` insert — covering both an `admitted` first attempt and a `duplicate`/`full`/`invalid_qr` first attempt.
2. A walk-in admission retried with the same idempotency key after the original committed returns the same `booking_id` without a second `session_bookings` row and without raising `'already has a booking'`.
3. The malformed-payload branch (`token_hash` null) retried with the same idempotency key returns the same row, not an incorrect mismatch error (`is not distinct from` NULL-safety check).
4. The same idempotency key presented with a different `token_hash`+`session_id` (QR) or a different `application_id`+`session_id` (walk-in) raises the distinct mismatch error, never returning stale data for a different request.
5. **Walk-in concurrency (backstop coverage, not the primary C1 regression test — that's test 2, run sequentially)**: two genuinely parallel `admit_walk_in` calls (e.g. `Promise.all` over two RPC calls with no client-side serialization, following the existing concurrency-test precedent in `tests/attendance/scan-attempt-concurrency-live.test.ts` and `tests/agenda/work-group-waitlist-live.test.ts`) with the same idempotency key both resolve to the same `booking_id`, with no `'already has a booking'` false rejection on either side. Note for whoever implements this: `Promise.all` alone doesn't force true overlap at the database level, so this test's value is as defense-in-depth coverage alongside test 2's sequential case, not as the sole proof the race is closed.
6. **QR idempotent replay changes the outcome correctly, concretely**: seed a session and one application such that WITHOUT idempotency the second of two identical-key calls would compute a *different* result than the first (e.g. the first call's admission makes the session newly non-full, so a naive second call recomputing from scratch would get `flexible_admitted` a second time instead of replaying the first call's actual stored result) — assert both calls return the identical `scan_attempts.id` and that exactly one `attendance_records` row and one `scan_attempts` row exist afterward, proving the idempotency check (not just luck) produced the replay.
7. A non-staff caller presenting a previously-used, valid idempotency key to `admit_walk_in` still gets `'Not authorized'` (idempotency check never bypasses the `is_staff()` gate).
8. A scanner whose assignment was revoked between its original (committed) attempt and a retry with the same key gets `'Not authorized for this session/room'` on the retry, not the original cached success. Note: in practice this specific case is caught client-side first by `verifyScannerScope`'s own pre-call check in `scan-qr-attempt.ts`, so a test exercising the in-RPC ordering itself must call `scan_qr_attempt_transactional` directly (bypassing the TypeScript pre-check) to actually exercise the TOCTOU window this check protects.
9. The malformed-payload branch's `scan_fingerprint` computation does not raise `SQLSTATE 42883` (confirms the `extensions.digest(...)` schema-qualification fix; this would have been silently broken by the original unqualified-`digest()` draft).
10. `scanQrAttemptConfirm` returns `{ ok: false, retryable: true, reason: 'lock-contention' }` for the advisory-lock-exhausted case, and `{ ok: false, retryable: false }` for a genuine scope-revocation — covering the tagged-union classification rules directly, not just their downstream client effects.
11. Existing callers (`scan-attempt.ts`'s direct path, `admission-management.ts`'s override path) continue to work unchanged with no idempotency key passed (`null` defaults, zero behavior change) — a straightforward regression check, not new behavior.
12. Client (component-level, not live DB): a non-retryable server rejection (e.g. the new mismatch error, or a scope-revoked rejection) does not enter the `retrying` loop — it goes straight to a terminal error message, matching the state machine's `SUBMIT_REJECTED` transition.
13. Client (component-level): a late-arriving response for a superseded attempt (cancelled, or an idempotency key that no longer matches the stale-response-guard ref) is discarded, never rendered.
14. Client (component-level): `CANCEL_RETRY` followed by a fresh `DETECT`/`SUBMIT_START` on the same QR payload generates a new idempotency key (not a reuse of the cancelled one).
15. Client (component-level): the single-flight guarantee extends correctly to the new `retrying` state — a `DETECT` action while in `retrying` is a no-op, same as while `submitting`.
16. Walk-in form: a retried submission after a transport failure reuses the same idempotency key across all retries of that one submission, and the session/identifier inputs are disabled while retrying.
17. The health-check Route Handler returns `401` when the caller's auth has expired, and the client treats this as a terminal "re-authenticate" state, not an infinitely-retried connectivity failure.
