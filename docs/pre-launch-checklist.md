## Notifications (sub-project 6)

- [ ] **Do not disable sandbox mode until the new unified notifications system has been verified via a real sandbox email, then delete the old `process-session-notifications` cron to avoid duplicate emails.**

  Context: `feature/notifications-layer` merged to `master` on 2026-10-08. It deliberately kept the old `process-session-notifications` cron (reading from `session_notification_outbox`) running alongside the new `process-notifications` cron (reading from the `notifications` table) for 3 overlapping event types — `session_cancelled`, `session_rescheduled`, `waitlist_promoted`. Both paths are live simultaneously right now, meaning these 3 event types currently send **2 duplicate emails** per real event. This was an explicit, accepted interim state (not an oversight) to avoid a risky hard cutover without first confirming the new cron actually sends mail correctly in the deployed/production environment — something that can't be verified from a local worktree.

  Required sequence, in order:
  1. Deploy this branch's changes to production.
  2. With sandbox mode still ON, trigger (or wait for) at least one real notification of each type and confirm the sandbox email actually arrives and looks correct — at minimum: `application_accepted`/`application_rejected`, `booking_confirmed`, one of `session_cancelled`/`session_rescheduled`/`waitlist_promoted`, `session_reminder`, `travel_reminder`, `announcement`.
  3. Confirm via a direct query that `notifications.email_status = 'sent'` rows are appearing for these events: `select channel, email_status, sent_at from notifications where email_status = 'sent' order by sent_at desc limit 10;`
  4. Only after that's confirmed: delete `src/app/api/cron/process-session-notifications/route.ts` and remove its entry from `vercel.json`, then redeploy.
  5. Only after the old cron is confirmed gone from the deployed cron schedule: sandbox mode may be turned off (set a real `sandbox_recipient_email` first if you want a staging-style redirect address, or disable `sandbox_enabled` entirely once ready for real participant traffic).

  Do not skip step 4 — turning off sandbox mode while both crons are still active would send every participant 2 real emails per cancellation/reschedule/waitlist-promotion event.

## Security audit (2026-10-11)

A comprehensive pre-launch audit (environment variables, notifications/cron coverage, database RLS/security posture, participant-facing flows, QR/attendance readiness) was run across the whole platform. Findings and status:

- [x] **Fixed and applied to production:** `rollback_import_batch_transactional` had a bare `if not is_staff() then` check with no `coalesce`. `is_staff()` returns NULL (not false) for any `authenticated` caller with no `public.profiles` row, and `if NULL` is falsy in plpgsql — so the exception never raised and the check (the function's *entire* authorization boundary, per its own comment) silently passed. This function is granted directly to `authenticated` and rolls back import batches (restoring/mutating PII like `full_name`, `phone`, `special_needs`) — genuinely exploitable. Fixed via `supabase/migrations/20261011000000_fix_is_staff_null_bypass_in_rpcs.sql`, which also hardened 4 sibling QR-lifecycle functions with the same bare pattern for consistency (confirmed NOT independently exploitable — each has an additional `v_caller.id is null` guard that already short-circuits the NULL case). Verified live against the real database post-apply.
- [x] **Fixed and applied to production:** a *different* bug, found while reviewing the above — `finalize_qr_issuance_for_server` / `finalize_qr_reissue_for_server` (and their two resolver helpers) re-check a staff requester's role at finalization time ("a staff member's role can lapse in the window between reservation and finalization"), but a 2026-09-29 role-consolidation migration had mechanically swapped the correct check (the *original requester's* role, `v_op.requested_by_auth_user_id`) for `is_staff()`, which checks the *current caller* instead. Both finalizers run via a service-role client (`auth.uid()` always NULL in that context), so the re-check never fired — a staff member whose role lapsed between request and finalization would still have their QR issued. Fixed via `supabase/migrations/20261012000000_fix_qr_finalizer_requester_role_check.sql`, restoring the correct recorded-requester check across all 4 functions. Verified live.
- [x] **Fixed and applied to production:** `public.qr_credentials` had row level security disabled — the one table missed when its 3 siblings (`qr_encryption_key_registry`, `qr_bulk_operation_batches`, `qr_lifecycle_operations`) all got `enable row level security` + revoke-from-anon/authenticated in the same original migration. Not actively exploitable (zero `anon`/`authenticated` grants existed on the table, and every real code path uses a service-role client), but fixed as defense-in-depth so a future migration can't accidentally grant access without RLS blocking it. Also hardened `count_distinct_travellers()` with a missing `set search_path` clause (the one SECURITY DEFINER function in the codebase without it — low severity, `service_role`-only). Both via `supabase/migrations/20261013000000_qr_credentials_rls_and_search_path_hardening.sql`. Verified live.
- [x] **Fixed:** `CRON_SECRET` protects 5 live cron routes but was never documented in `.env.local.example`. Added.
- [x] **Corrected understanding (no fix needed):** the "2 duplicate emails per event" risk described in the Notifications section above is **not currently live** — neither the old `process-session-notifications` cron nor the new `process-notifications` cron is actually firing in production right now, since no external cron-job.org jobs have been set up yet for either (only `travel-reminders` is Vercel-scheduled). The duplication risk becomes real only once external cron jobs are configured for both — the required sequence in the Notifications section above (verify new system first, delete old cron, *then* set up external jobs) still stands and avoids the risk entirely if followed in order.
- [ ] **Not yet verified:** whether any notification type (`application_accepted`/`rejected`, `booking_confirmed`, `session_cancelled`/`rescheduled`, `waitlist_promoted`, `session_reminder`, `travel_reminder`, `announcement`) has actually been confirmed sent in production — this remains blocked on `RESEND_API_KEY`/`RESEND_FROM_EMAIL` being unset in Vercel (see Resend configuration section).

Not a blocker for the primary registration/attendance flow, but will show fabricated room names to real participants if launched as-is.

  1. Confirm `QR_ENCRYPTION_KEY_V1` is set as a real secret in Vercel's environment variables (confirmed present in local `.env.local` only; fails closed — throws — if unset in production, rather than silently succeeding).
