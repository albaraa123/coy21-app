## Live test-suite fixture leak and cleanup (2026-10-13/14)

A full `npx vitest run` against the live linked COY21 project (triggered during the RCOY-branding cleanup work, to confirm nothing broke) left ~123 `@test.local` fixture accounts and ~177 associated test rows (rooms, sessions, conference days, session types, tracks, tags, people, applications) in the real production database — some live tests' `afterAll` cleanup apparently didn't complete (one explicit cleanup error was observed: an `import_rows_duplicate_of_row_id_fkey` violation), and the pollution cascaded since later tests shared/collided with the orphaned fixtures (147 of 1503 tests failed in that run, vs. the documented ~7-failure baseline).

- [x] **Found and fully cleaned up (2026-10-14).** Verified every polluted table's rows were test fixtures (not real data) via `created_at` timestamps — all fell in a tight `2026-10-13 19:53–20:09 UTC` window matching the test run, with zero exceptions in `rooms`/`session_types`/`conference_days`/`sessions`/`tags`/`people`, and exactly 1 pre-existing real row in `tracks` (the "General" track from 2026-10-08) and 5 pre-existing real `auth.users` accounts. Full backup taken first (`C:\Users\albar\.claude\backups\coy21\coy21-backup-20261014-test-fixture-cleanup\`, outside the repo — includes the full fixture user list, full config-table row dumps, and the final cleanup SQL run). Cleanup script scoped entirely by this timestamp cutoff, run manually via the Supabase SQL Editor (Claude Code's own auto-mode classifier correctly blocked running a deletion this large directly). Verified after: `rooms`/`session_types`/`conference_days`/`sessions`/`tags`/`people` all back to 0, `tracks` back to 1 (the real row), all 5 kept accounts (`albaraak2002@gmail.com`, `albaraa.coy21@gmail.com`, `albaraaalbadwi@gmail.com`, `albaraa.scale.om@gmail.com`, `albaraa@scaleagency.om`) intact with correct roles.
- [x] **Known, permanent, by-design residue: 14 test `auth.users` accounts and 14 `applications` could not be deleted.** `qr_credentials` and `qr_lifecycle_operations` are enforced append-only by dedicated triggers (`qr_credentials_enforce_lifecycle_trigger` / `qr_lifecycle_operations_enforce_lifecycle_trigger`, both literally raise `'... rows are never deleted, only transitioned'` on any `DELETE`) — this is deliberate QR security/audit-trail design, confirmed by reading the trigger source, not a bug to work around. This residue is small, clearly identifiable (all still fall in the same `@test.local`/2026-10-13 window), and harmless — it does not affect the real 5 kept accounts, the real "General" track, or any other real data.
- [x] **Follow-up fixes (2026-10-14): the undeletable residue was still visible in two real admin pages.** 4 of the 14 accounts had `role = 'super_admin'` from the leaked test run, so they appeared in Staff Management as fake staff — demoted all 4 back to `role = 'participant'` directly in the database (same end-user-visible result as deletion, Staff Management has no other "hide" mechanism). The Applications list (`src/app/[locale]/(admin)/applications/page.tsx`) has no role lever to use the same trick, so added a `.not('profiles.email', 'ilike', '%@test.local')` filter to both its count and data queries instead — display-only, the rows still exist, verified directly against the live database before committing (13 fixture rows excluded, the one real non-test-suite scratch application on a kept account still shows correctly).
- [x] **Root cause found and fixed (2026-10-14).** `import_rows.duplicate_of_row_id` is a self-referencing FK; `tests/import/validation-live.test.ts` and `tests/import/confirm-import-live.test.ts` both deliberately seed a within-batch duplicate row to test duplicate-detection, which sets this self-reference via the real pipeline — but each file's `afterAll` bulk-deleted the batch's `import_rows` in one unordered statement with no guarantee Postgres processes the referencing row first, exactly matching the `import_rows_duplicate_of_row_id_fkey` error seen during this incident. Fixed both to null out `duplicate_of_row_id` for the whole batch before deleting. Audited the other 6 live import test files for the same pattern (via a dedicated research pass) — none currently seed within-batch duplicates, so none are at risk today, though a few would become vulnerable if their fixtures changed to introduce one; not fixed preemptively, noted for future awareness only. Full live suite should be safe to re-run now, though prefer targeted test files over the full suite against the live project when possible regardless, as a matter of blast-radius discipline.
- [x] **Found and fixed a third spot showing the same residue (2026-10-18): the admin Dashboard's "Accepted participants" card.** Showed "11" against a database that should only have 1 real accepted application — the other 10 are the same undeletable `@test.local` fixtures. Fixed `getAcceptedParticipantCount()` (`src/lib/dashboard/admin-dashboard-queries.ts`) to exclude them, after finding and working around two real PostgREST gotchas along the way (both confirmed directly against the live database before landing on the final query shape): `.not(col, 'ilike', ...)` silently drops every row where `col` is NULL, since SQL's `NOT(NULL ILIKE x)` evaluates to NULL and `WHERE` treats that as exclude — fixed with an explicit `.or(...is.null,...)`; and `.not('joined.col', 'ilike', ...)` against a non-`!inner` join doesn't restrict rows at all (same caveat already on the Applications-list page) — resolved with two separate counts (base, minus a `!inner`-scoped "claimed and test-linked" count) instead of one combined filter. Updated the one live test whose premise predated this whole incident (it asserted a freshly-inserted `@test.local` application MUST inflate the dashboard count — now asserts the opposite, plus a new sibling test proving a real application still counts normally). Also found and deleted two further leftover rows during this pass, both confirmed zero-dependent before deleting: one orphaned `import_batches` row the original cleanup missed (`uploaded_by` was NULL, not a `cutoff_user_ids` match — this was *also* the reason "Imports requiring attention" showed a false positive), and one manually-created "Test Gate" `staff_assignments` row from an earlier admin-UI walkthrough (a real account, not the automated leak, just forgotten scratch data).
- [x] **Found and fixed a separate, more serious bug while checking the same residue on the Reports page (2026-10-18): the Applications & Confirmation metrics have been silently showing all zeros in production.** `src/app/[locale]/(admin)/reports/page.tsx` used PostgREST's `count:id.count()` aggregate-function query shape — confirmed directly against the live database that aggregate functions are disabled on this Supabase project (every such call fails with `PGRST123`, "Use of aggregate functions is not allowed"). The error was never checked, so the query silently fell back to an empty array — not a visible error, just wrong-looking-like-correct zeros, for as long as this page has existed. Rewrote both queries (`byType`/`byStatus`) to fetch raw `applications` rows and aggregate in application code instead, which also naturally lets the same `@test.local` exclusion filter apply here (same residue as the Dashboard fix above). Also fixed the same missing filter on the "accepted participants" CSV export (`src/app/api/admin/reports/participants-csv/route.ts`) — a real staff export would have included 10 fake test rows (fabricated names/emails) alongside the 1 real participant. Both fixes verified directly against the live database before committing: the Reports query now correctly returns 1 real accepted application (down from 14 total rows fetched), and the CSV export returns 1 real row (down from 11 raw `accepted` rows). Confirmed via a full-codebase grep that `count:id.count()` was the only aggregate-function usage anywhere — no other page has this specific silent-failure bug.
- [x] **Allocation-engine risk (found 2026-10-23) fully resolved (2026-10-24/25): the root data, not just the symptom, is now gone.** A code-level `@test.local` filter inside `run-extraction.ts`/`run-allocation.ts` was tried and reverted (it broke `tests/allocation/run-behavioral.test.ts`, since `@test.local` is this codebase's own standard live-test-fixture domain project-wide, not unique to this incident — see history below). ## Security audit (2026-10-11)

A comprehensive pre-launch audit (environment variables, notifications/cron coverage, database RLS/security posture, participant-facing flows, QR/attendance readiness) was run across the whole platform. Findings and status:

- [x] **Fixed and applied to production:** `rollback_import_batch_transactional` had a bare `if not is_staff() then` check with no `coalesce`. `is_staff()` returns NULL (not false) for any `authenticated` caller with no `public.profiles` row, and `if NULL` is falsy in plpgsql — so the exception never raised and the check (the function's *entire* authorization boundary, per its own comment) silently passed. This function is granted directly to `authenticated` and rolls back import batches (restoring/mutating PII like `full_name`, `phone`, `special_needs`) — genuinely exploitable. Fixed via `supabase/migrations/20261011000000_fix_is_staff_null_bypass_in_rpcs.sql`, which also hardened 4 sibling QR-lifecycle functions with the same bare pattern for consistency (confirmed NOT independently exploitable — each has an additional `v_caller.id is null` guard that already short-circuits the NULL case). Verified live against the real database post-apply.
- [x] **Fixed and applied to production:** a *different* bug, found while reviewing the above — `finalize_qr_issuance_for_server` / `finalize_qr_reissue_for_server` (and their two resolver helpers) re-check a staff requester's role at finalization time ("a staff member's role can lapse in the window between reservation and finalization"), but a 2026-09-29 role-consolidation migration had mechanically swapped the correct check (the *original requester's* role, `v_op.requested_by_auth_user_id`) for `is_staff()`, which checks the *current caller* instead. Both finalizers run via a service-role client (`auth.uid()` always NULL in that context), so the re-check never fired — a staff member whose role lapsed between request and finalization would still have their QR issued. Fixed via `supabase/migrations/20261012000000_fix_qr_finalizer_requester_role_check.sql`, restoring the correct recorded-requester check across all 4 functions. Verified live.
- [x] **Fixed and applied to production:** `public.qr_credentials` had row level security disabled — the one table missed when its 3 siblings (`qr_encryption_key_registry`, `qr_bulk_operation_batches`, `qr_lifecycle_operations`) all got `enable row level security` + revoke-from-anon/authenticated in the same original migration. Not actively exploitable (zero `anon`/`authenticated` grants existed on the table, and every real code path uses a service-role client), but fixed as defense-in-depth so a future migration can't accidentally grant access without RLS blocking it.
